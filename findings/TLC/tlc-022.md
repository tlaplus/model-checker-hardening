# Equality of function sets is wrong when a domain or co-domain is empty

## Summary

**Fixed in https://github.com/tlaplus/tlaplus/pull/1408**

TLC decided `[S1 -> T1] = [S2 -> T2]` by comparing `S1` with `S2` and `T1` with
`T2`. That rule fails when a set is empty. If `S1 = S2 = {}`, both sets are
`{<<>>}` whatever `T1` and `T2` are. If `T1 = T2 = {}` and `S1`, `S2` are
nonempty, both sets are empty whatever `S1` and `S2` are. TLC answered `FALSE`
in both cases. This is a soundness defect: an invariant that holds is reported
as violated, and an action that compares such sets is disabled.

TLC was also inconsistent with itself. `\subseteq` holds in both directions,
and the fingerprints and `compareTo` of the two values are equal, but `=`
answers `FALSE`. State deduplication and the next-state relation therefore
disagree about the same values.

This was filed upstream as
[tlaplus/tlaplus#1407](https://github.com/tlaplus/tlaplus/issues/1407) before
this project opened issues from findings systematically, and is recorded here
afterwards. It came out of the same differential comparison as
[`apalache-bmc-002`](../apalache-bmc/apalache-bmc-002.md), where Apalache got
the reflexive equality of `[{} -> {}]` wrong. TLC handled that exact input,
because both sides have the same domain and co-domain, but not the variants
whose domains or co-domains differ. The Apalache counterparts were filed as
[apalache-mc/apalache#3476](https://github.com/apalache-mc/apalache/issues/3476)
and [#3477](https://github.com/apalache-mc/apalache/issues/3477).

Fixed by [PR #1408](https://github.com/tlaplus/tlaplus/pull/1408); the issue
was closed on 2026-09-09. Reproduced with the tla2tools snapshot of 2026-09-08
(`1.8.0-20260908.182438-58`, tlaplus/tlaplus commit `b123b22`), and not with
the snapshot of 2026-09-10 (`1.8.0-20260910.135024-64`, commit `8ab94b6`) or
later.

## Reproduction

`EmptyFcnSetEq.tla` evaluates the comparisons in `ASSUME`:

```tla
---- MODULE EmptyFcnSetEq ----
EXTENDS TLC
ASSUME PrintT(<<"empty domain", [{} -> {1}] = [{} -> {2}]>>)
ASSUME PrintT(<<"empty co-domain", [{1} -> {}] = [{2} -> {}]>>)
ASSUME PrintT(<<"subset both ways", [{1} -> {}] \subseteq [{2} -> {}] /\ [{2} -> {}] \subseteq [{1} -> {}]>>)
====
```

```sh
java -cp tla2tools.jar tlc2.TLC EmptyFcnSetEq.tla   # with an empty EmptyFcnSetEq.cfg
```

TLC `b123b22` prints:

```text
<<"empty domain", FALSE>>
<<"empty co-domain", FALSE>>
<<"subset both ways", TRUE>>
```

All three are `TRUE`. In a model, the wrong equality becomes a spurious
violation. `EmptyCodomain.tla`:

```tla
---- MODULE EmptyCodomain ----
VARIABLE fs
Init == fs = [{1} -> {}]
Next == UNCHANGED fs
\* Both sides are the empty set, so the invariant holds in every state.
Inv == fs = [{2} -> {}]
====
```

with `EmptyCodomain.cfg`:

```text
INIT Init
NEXT Next
INVARIANT Inv
```

TLC `b123b22` exits with status 12:

```text
Error: Invariant Inv is violated by the initial state:
fs = {}
```

## Expected behavior

All three comparisons are `TRUE`, and `EmptyCodomain` has no error. TLC
`8ab94b6` and `d8fb231` print `TRUE` three times and report `No error has been
found.` Apalache 0.62.3 (build `3eb15b2`) also proves `Inv` of `EmptyCodomain`,
with `{}` annotated as `Set(Int)`.

## Root cause

`SetOfFcnsValue.equals` compared domains and co-domains pairwise without
first checking whether either function set is empty. The comparison dated from
the initial import of TLC. `SetOfRcdsValue.equals` and
`SetOfTuplesValue.equals` had received an `isEmpty()` check for the same class
of bug in 2014, but `SetOfFcnsValue` had not. The fix decides whether either
function set is empty before it compares domains and co-domains.

## Verification

- FuzzTLA `4bbaf66c`; TLC `b123b22` (reproduces), `8ab94b6` and `d8fb231`
  (fixed); Apalache 0.62.3, build `3eb15b2` (agrees with the fixed TLC).
