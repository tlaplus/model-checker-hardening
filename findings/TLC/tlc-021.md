# An evaluation error in a successor state two or more steps deep ends TLC with `System.exit(1)`

## Summary

When fingerprinting a successor state raises an evaluation error, TLC reports
the error and prints the behavior that leads to the state. If the predecessor
of the failing state is not initial, TLC re-generates the failing state to
print it, cannot find it, prints "Failed to recover the initial state from its
fingerprint" and "This is probably a TLC bug(5)", and calls `System.exit(1)`.
`TLC.process()` never returns. Exit status 1 is not one of TLC's exit codes,
and an application that runs TLC in its own JVM is terminated with it. When the
failing state is the first successor of an initial state, the same error ends
with exit status 75.

The state cannot be found because TLC compares the re-generated candidates with
the failing state by `equals`, which raises the same evaluation error, and the
lookup treats that error as "not equal".

This is [tlaplus/tlaplus#815](https://github.com/tlaplus/tlaplus/issues/815),
open since 2023, whose reproduction puts `{...} \cup [field |-> "value3"]` into
the third state. The issue describes the misleading message. This finding adds
the cause, the exit status, and the infinite values that reach the same path in
generated modules.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20261023.040326-108`, tlaplus/tlaplus commit `606dfa4`), FuzzTLA
`e180a389`, and Apalache 0.62.3 (`3eb15b2`, not involved), on OpenJDK 25.0.4.1
for Linux aarch64.

## Reproduction

`TraceRecovery.tla`:

```tla
---- MODULE TraceRecovery ----
EXTENDS Integers
VARIABLES x, n
Init == x = <<1>> /\ n = 0
Next == /\ n < 2
        /\ n' = n + 1
        /\ x' = IF n = 1 THEN [i \in Int |-> i] ELSE <<2>>
====
```

`TraceRecovery.cfg`:

```text
INIT Init
NEXT Next
```

```sh
java -XX:+UseParallelGC -cp tla2tools.jar tlc2.TLC -workers 1 -deadlock \
  -noGenerateSpecTE -config TraceRecovery.cfg TraceRecovery.tla
echo $?
```

```text
Error: TLC threw an unexpected exception.
This was probably caused by an error in the spec or model.
See the User Output or TLC Console for clues to what happened.
The exception was a java.lang.RuntimeException
: Attempted to compute the number of elements in the overridden value Int.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ n = 0
/\ x = <<1>>

State 2: <Next line 5, col 9 to line 7, col 58 of module TraceRecovery>
/\ n = 1
/\ x = <<2>>

Error: Failed to recover the initial state from its fingerprint.
Error: This is probably a TLC bug(5).
State :
/\ n = 2
/\ x = [i \in Int |-> <expression line 7, col 46 to line 7, col 46 of module TraceRecovery>]
1
```

With `-workers 4`, the result is the same. With `IF n = 0`, the function is the
first successor of the initial state: TLC prints only state 1 and exits with
status 75. The module of #815 also exits with status 1 at `606dfa4`.

## Cause

From `tlatools/org.lamport.tlatools/src/tlc2/tool` at `606dfa4`:

1. A worker computes the fingerprint of a successor `s2` of `s1`. Normalizing
   `[i \in Int |-> i]` needs the cardinality of `Int` and throws a
   `RuntimeException`. `ModelChecker` reports it as an error and calls
   `trace.printTrace(curState, succState)` (`ModelChecker.java:678`;
   `Worker.java:562` and `594` with several workers).
2. `TLCTrace.printTrace` (`TLCTrace.java:349`) prints the prefix up to `s1`.
   To print `s2` with the action that produced it, it calls
   `tool.getState(s2, s1)` (`TLCTrace.java:428`). When that returns null, it
   prints `TLC_FAILED_TO_RECOVER_INIT` and `TLC_BUG` "5", prints `s2`
   standalone, and calls `System.exit(1)` (`TLCTrace.java:429-433`).
3. `Tool.getState(TLCState, TLCState)` (`Tool.java:3805`) re-generates the
   successors of `s1` and returns the first `state` with `s2.equals(state)`.
   Comparing two functions over `Int` raises the evaluation error of step 1
   again. The `catch (TLCRuntimeException e) { continue; }` at `Tool.java:3818`,
   added for [tlaplus/tlaplus#743](https://github.com/tlaplus/tlaplus/issues/743)
   to skip successors whose values are incomparable with `s2`, also skips the
   successor that is `s2`. No candidate matches, and the method returns null.

When `s1` is initial, `printTrace` takes the branch at `TLCTrace.java:351`,
which also calls `tool.getState(s2, s1)` (`TLCTrace.java:364`) but does not
check for null. It omits `s2` from the trace and returns, so the error ends
with status 75.

## Corpus evidence

The `graph` corpus71 run, with the recursion library of
[recursive operators](../../docs/manual/recursive-operators.md), has 30 TLC
crashes of this kind among its 1,260 TLC crashes, for example `00eb6c89`,
`03c9293f` and `15e6e5a8`. In all of them, the worker diagnostic is "TLC
worker exited while processing the input", followed by the TLC output that the
worker's shutdown hook prints, ending in `TLC bug(5)`. The error message and the
value of the failing state are:

| Error message | Infinite value in the failing state | Entries |
| --- | --- | ---: |
| `Attempted to compute the number of elements in the overridden value` | a function over `Nat` | 16 |
| `Attempted to compute the number of elements in the overridden value` | a function over `Int` | 6 |
| `Attempted to enumerate S \cup T`, `S \ T` or `{ x \in S : p(x) }` | a set over `Int` or `Nat` | 8 |

The trace before the failing state has 2 to 10 states. In `00eb6c89`, action
`Node4` assigns `var0' = [arg12 \in Int |-> SetSum({1, 2, 3}) ^ arg12]` in the
fifth state.

Without the worker's exit, these errors are the conformance differences
[function over an infinite domain](../../conformance/function-over-infinite-domain.md)
and [infinite set as a state value](../../conformance/infinite-set-as-state-value.md),
which TLC reports with status 75. [tlc-003](tlc-003.md) is a different path: the
same messages escape as error 1000 with status 255 while TLC computes initial
states.

## Expected behavior

TLC reports the evaluation error with the exit status it uses when the failing
state is a first successor, 75, and `TLC.process()` returns. Two possible
changes:

- `Tool.getState(TLCState, TLCState)` compares fingerprints first, as
  `getState(long, TLCState)` does, and uses `equals` only to tell apart
  candidates with the fingerprint of `s2`. For `s2` itself, the fingerprint is
  the value whose computation failed, so `printTrace` would also need its
  fallback.
- `printTrace` treats a null result for `s2` as it does in the initial-state
  branch: it prints `s2` standalone, without its action, and returns instead of
  calling `System.exit(1)`. The error was already reported, so the trace is
  only incomplete, not wrong.

The message "Failed to recover the initial state" names the wrong state: TLC
recovers the initial state, but not `s2`. A comment in
`ConcurrentTLCTrace.java` already calls this message misleading for the
non-initial case.

## Impact

An application that embeds TLC, such as a test harness, an IDE or a service,
loses its JVM, as with [tlc-019](tlc-019.md). A user of the command line sees
"This is probably a TLC bug" after an ordinary evaluation error in the
specification, which makes the error harder to diagnose, as #815 reports. Whether a
specification hits this path depends only on how deep the failing state is.
