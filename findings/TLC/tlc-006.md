# Bounded `CHOOSE`, `\E` and set comparison materialize an interval, ignoring the enumeration limit

## Summary

When TLC evaluates `CHOOSE x \in a .. b : P` or `\E x \in a .. b : P`, it
enumerates the interval through `EnumerableValue.elements(Ordering)`. For an
`IntervalValue` that call is `toSetEnum()`, which allocates one `Value[]` slot
per element. TLC's 1,000,000-element enumeration limit is not consulted on this
path. `CHOOSE x \in 1 .. 2000000 : TRUE` evaluates to `1`, while
`CHOOSE x \in {y \in 1 .. 2000000 : TRUE} : TRUE` reports
`Attempted to construct a set with too many elements (>1000000)`.

Past the heap, the allocation fails. With `-Xmx512m`, `1 .. 5000000` completes
and `1 .. 20000000` runs out of memory. TLC reports error 1001, and a JVM
started with `-XX:+ExitOnOutOfMemoryError` terminates.

This is the root cause of [`tlc-005`](tlc-005.md) on a different path. In
`tlc-005` the allocation happens during action decomposition, where TLC
swallows the error, so only a JVM with `-XX:+ExitOnOutOfMemoryError` fails.
Here it happens during ordinary evaluation, and both JVM configurations fail.

Comparing an interval with a set that is not an interval materializes it in
the same way; see [Reached through set comparison](#reached-through-set-comparison).

The frames below are from the `hs_err` report of a run with
`-XX:+UnlockDiagnosticVMOptions -XX:AbortVMOnException=java.lang.OutOfMemoryError`.
For the bounded `CHOOSE`, the bound is enumerated directly by
`Tool.evalApplImpl`, after the `inVal.normalize()` call that
[`tlc-004`](tlc-004.md) cites:

```text
j tlc2.value.impl.IntervalValue.toSetEnum()
j tlc2.value.impl.EnumerableValue.elements(Enumerable$Ordering)
j tlc2.tool.impl.Tool.evalApplImpl(OpApplNode, Context, TLCState, TLCState, int, CostModel)
```

For `\E`, the enumeration goes through `Tool.contexts`:

```text
j tlc2.value.impl.IntervalValue.toSetEnum()
j tlc2.value.impl.EnumerableValue.elements(Enumerable$Ordering)
j tlc2.tool.impl.Tool.contexts(...)
j tlc2.tool.impl.Tool.contexts(...)
j tlc2.tool.impl.Tool.evalApplImpl(OpApplNode, Context, TLCState, TLCState, int, CostModel)
```

The `corpus16` run contains one TLC crash with this cause. Its initial
predicate evaluates `CHOOSE bound73 \in -1360104906 .. (CASE ...)`. See the
[`d21312f3...` input](../../corpus16/02tlc-crash/d21312f3c4a78c0f271eda264ad8873facbe39c28db59975fe797eeb19f62860.cbor)
and its [stacktrace](../../corpus16/02tlc-crash/d21312f3c4a78c0f271eda264ad8873facbe39c28db59975fe797eeb19f62860.stacktrace).
The stored text is again one `OutOfMemoryError` line, the same as for
`tlc-004` and `tlc-005`, so this finding has no triage signature either.

Observed with the TLC snapshot bundled in FuzzTLA on 2026-09-13
(`tla2tools` 1.8.0-SNAPSHOT, 2026-09-12).

## Reproduction

```tla
---- MODULE Repro ----
EXTENDS Integers

ASSUME (CHOOSE x \in 1 .. 411248002 : TRUE) = 1

====
```

with an empty `Repro.cfg`. Run:

```sh
java -Xmx512m -cp tla2tools.jar tlc2.TLC -workers 1 -nowarning Repro
```

```text
Error: Java ran out of memory.  Running Java with a larger memory allocation
pool (heap) may fix this.  But it won't help if some state has an enormous
number of successor states, or if TLC must compute the value of a huge set.
```

With `-XX:+ExitOnOutOfMemoryError`:

```text
Terminating due to java.lang.OutOfMemoryError: Java heap space
```

`ASSUME \E x \in 1 .. 411248002 : x = 1` fails in the same way. Wrapping the
interval in a filter, `CHOOSE x \in {y \in 1 .. 411248002 : TRUE} : TRUE`,
reports the enumeration limit instead:

```text
Attempted to construct a set with too many elements (>1000000).
```

## Reached through `ApaFoldSet`

The `corpus19` run contains one TLC crash with this cause. Its initial
predicate applies `ApaFoldSet` to `-29849 .. 291752219`. TLC's `Apalache.tla`
defines the operator recursively with a bounded `CHOOSE` over the folded set:

```tla
ApaFoldSet(__Op(_,_), __v, __S) ==
    IF __S = {}
    THEN __v
    ELSE LET __w == CHOOSE __x \in __S: TRUE IN
         LET __T == __S \ {__w} IN
         ApaFoldSet(__Op, __Op(__v,__w), __T)
```

so the first unfolding enumerates the interval. The crash is entry `f2465313`,
whose stored diagnostic is the single `OutOfMemoryError` line. With `-Xmx512m -XX:+ExitOnOutOfMemoryError`, the module

```tla
---- MODULE Repro ----
EXTENDS Integers, Apalache
VARIABLE x
Op(a, b) == a
Init == x = ApaFoldSet(Op, 0, -29849 .. 291752219)
Next == UNCHANGED x
====
```

terminates with `java.lang.OutOfMemoryError: Java heap space` while computing
initial states, as does `Init == x = CHOOSE y \in -29849 .. 291752219 : TRUE`.
`ApaFoldSet(Op, 0, 1 .. 20)` evaluates normally.

## Reached through set comparison

`IntervalValue.equals` calls `toSetEnum()` when its argument is not an
interval, and `SetEnumValue.compareTo` does the same when it sorts an interval
against an enumerated set. A set literal sorts its elements when it is
normalized, so an interval inside a set of sets is materialized as soon as TLC
compares or fingerprints that set. The cardinalities differ, so neither
comparison needs the elements.

```tla
---- MODULE Repro ----
EXTENDS Integers
VARIABLE x
Init == x = 1
Next == UNCHANGED x
Inv == (1 .. 479001600) = {1, 2, 3}
====
```

With `INIT Init`, `NEXT Next`, `INVARIANT Inv` and `-Xmx512m`, TLC fails in
0.3 seconds with exit 255:

```text
Error: Out Of Memory. There are probably too many initial states.
```

The specification has one initial state. With `-Xlog:exceptions=info` the
error is thrown at

```text
tlc2.value.impl.IntervalValue.toSetEnum()
tlc2.value.impl.IntervalValue.equals(Object)
tlc2.tool.impl.Tool.evalApplImpl(...)
```

The same happens for these invariants:

| `Inv` | Result |
| --- | --- |
| `(1 .. 479001600) \in {{1, 2, 3}}` | out of memory, exit 255 |
| `{1 .. 479001600, {1, 2, 3}} # {}` | out of memory in `SetEnumValue.compareTo`, under `SetEnumValue.normalize` |
| `{1 .. 479001600, 1 .. 5} # {}` | pass: two intervals compare without materializing |
| `{1 .. 479001600} # {}` | pass: one element needs no sorting |
| `(1 .. 2000000) # {1, 2, 3}` | pass, although the interval exceeds the enumeration limit |
| `{y \in 1 .. 2000000 : TRUE} # {1, 2, 3}` | `Attempted to construct a set with too many elements (>1000000)`, exit 75 |

corpus58 contains one TLC crash with this cause, `6edda33c`, stored as
`Terminating due to java.lang.OutOfMemoryError: Java heap space`. Its invariant
filters the set `{var0 .. IntFactorial(IntFib(3 * step)), {1, 2, 3}, ...}`.
The recursion library clamps `IntFactorial` at 12, so in the state with
`step = 3` the interval has 479,001,600 elements, and four reachable states
suffice to exhaust a 512 MB heap.

Reproduced with FuzzTLA commit `0dcbb309056087d3fc8903ddc4e7aae3c594d130` and
TLC commit `0dab95e` (tla2tools `1.8.0-20261001.024819-90`), bundled in
FuzzTLA, with OpenJDK 25.0.4.1 on Linux aarch64. Apalache was not rerun; the corpus58 input also
contains a non-constant interval, which Apalache rejects
([nonconstant-integer-range](../../conformance/nonconstant-integer-range.md)).

## Expected behavior

The enumeration limit should apply to every enumeration of an interval. A
bound above the limit should report `Attempted to construct a set with too
many elements`. Better, `CHOOSE` and `\E` could iterate an interval lazily,
since both can stop at the first witness and neither needs the elements in an
array. Comparing an interval with another set should first compare
cardinalities, and otherwise test membership element by element, without
building an array.

## Impact

The memory a check needs depends on a constant in the specification, not on
the reachable state space, so raising the heap only moves the threshold. A
consumer records a generic out-of-memory crash that cannot be told apart from
`tlc-004` or `tlc-005` using the stored evidence.
