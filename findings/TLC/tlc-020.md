# Workers that share the value of an action's `\E` parameter sort it concurrently and corrupt it

## Summary

When the next-state action contains `\E p \in S : A` and `S` is constant, TLC
splits the action at startup: it enumerates `S` once and creates one `Action`
per element, with `p` bound to that element in the action's context. The bound
value is neither normalized nor copied per worker, so every worker shares it.
If `A` assigns `p` to a variable, the workers fingerprint states that hold the
same set object, and each fingerprint first normalizes the set by sorting its
element array in place without synchronization. Two workers that sort the set
at the same time can duplicate one element and lose another. The set is then
marked as normalized, and TLC treats it as a valid value from then on. A bound
given by a zero-arity definition is not affected, because TLC normalizes the
values of such definitions at startup.

With more than one worker, TLC therefore checks states whose values no TLA+
expression can produce, such as `{FALSE, FALSE}` or `{7, 1, 3, 4, 5, 6, 7, 8}`.
It reports invariant violations that do not exist, and it counts distinct states
that do not exist. With one worker, the same specification passes.

This is the root cause of tlaplus/tlaplus issue
[#1445](https://github.com/tlaplus/tlaplus/issues/1445), "TLC can miss states
due to unnormalized values", whose examples pass a constant set as an operator
argument in `Next` and show missed states. This finding adds a second way to
reach the shared value, an `\E` parameter, and a second symptom: corrupted
values that cause spurious counterexamples. The open pull request
[#1448](https://github.com/tlaplus/tlaplus/pull/1448) sorts shared sets on a
copy. With it, the reproduction below passed in all of 100 runs.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20261020.183738-107`, tlaplus/tlaplus commit `d2e1472`, which is also
the head of `master` on 2026-10-22), FuzzTLA `4206d99`, and Apalache 0.62.3
(`3eb15b2`, not involved), on OpenJDK 25.0.4.1 for Linux aarch64 with 8 cores.

## Reproduction

`SharedSet.tla`:

```tla
---- MODULE SharedSet ----
EXTENDS Naturals
VARIABLES n, x
Init == n \in 1..2000 /\ x = {}
Next == \E p \in {{8, 7, 6, 5, 4, 3, 2, 1}} : x = {} /\ x' = p /\ UNCHANGED n
Inv == x \in {{}, 1..8}
====
```

`SharedSet.cfg`:

```text
INIT Init
NEXT Next
INVARIANT Inv
```

The only value `p` can take is `1..8`, so `Inv` holds and there are 4000
reachable states. The 2000 initial states let all workers evaluate `Next` from
the start.

```sh
java -XX:+UseParallelGC -jar tla2tools.jar -workers 4 -deadlock SharedSet.tla
```

```text
Error: Invariant Inv is violated.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ n = 2
/\ x = {}

State 2: <Next line 5, col 47 to line 5, col 77 of module SharedSet>
/\ n = 2
/\ x = {7, 1, 3, 4, 5, 6, 7, 8}
```

Outcomes of 100 runs each:

| TLC | `-workers` | Result |
| --- | --- | --- |
| `d2e1472` | 4 | 25 report `Inv` violated (exit 12); 75 pass with 4000 states |
| `d2e1472` | 1 | 100 pass with 4000 states |
| PR #1448 at `f4bf8de` | 4 | 100 pass with 4000 states |

The value of `x` in the violating state differed between runs. Every such value
was unsorted, had duplicate elements, or lacked some of `1..8`, for example
`{1, 1, 2, 3, 4}`, `{1, 2, 7, 3, 5, 7, 8, 8}` and `{1, 3, 4, 5, 6, 7, 8}`.

Variants with 4 workers show that the value must reach the split action
without being normalized first:

| Variant of `Next` | Runs | Violations |
| --- | --- | --- |
| `\E p \in Q(1)` with `Q(k) == {{8, 7, 6, 5, 4, 3, 2, k}}` | 60 | 10 |
| `\E p \in Q` with `Q == {{8, 7, 6, 5, 4, 3, 2, 1}}` | 60 | 0 |
| `x' = {{TRUE, FALSE}, {TRUE, FALSE}, {TRUE, FALSE}}`, no `\E` | 40 | 0 |
| `\E p \in IF n > 0 THEN {...} ELSE {}` | 40 | 0 |

TLC evaluates the zero-arity definition `Q` at startup and normalizes its value
deeply (see [Cause](#cause)). Without `\E`, each evaluation of `Next` creates a
fresh set. A bound that depends on the state keeps TLC from splitting the
action, so the bound is evaluated anew for each state.

A two-element set suffices. With
`Next == \E p \in {{TRUE, FALSE}} : x = {} /\ x' = p /\ UNCHANGED n` and
`Inv == x \in {{}, {TRUE, FALSE}}`, 1 of 40 runs reported `x = {FALSE, FALSE}`.

## Cause

From `tlatools/org.lamport.tlatools/src/tlc2` at `d2e1472`:

1. `Tool.getActionsAppl` splits `\E` (`tool/impl/Tool.java:375-391`). It
   enumerates the bound once with `contexts(...)` and calls `getActions` with
   each resulting context. That context, which binds `p` to the element of the
   bound, becomes `Action.con` (`tool/Action.java:43`), and every worker
   evaluates the action in it (`Tool.java:898`). The element is not normalized.
   Here it is the inner `SetEnumValue` `{8, 7, …, 1}`. The outer singleton
   needs no comparison to sort, so its element is never normalized as a side
   effect.
2. `x' = p` stores that object in the successor state. Before enqueuing the
   state, a worker computes its fingerprint, and `SetEnumValue.fingerPrint`
   calls `normalize()` first (`value/impl/SetEnumValue.java:348-350`).
3. `SetEnumValue.normalize()` (`SetEnumValue.java:269-275`) calls
   `elems.sort(true)` and then sets the plain field `isNorm`. `ValueVec.sort`
   (`value/impl/ValueVec.java:172-203`) is an insertion sort that shifts the
   elements of the shared array in place and finally overwrites
   `elementCount`.

For `[TRUE, FALSE]`, one interleaving is the following. Worker A reads
`FALSE`, finds it smaller than `TRUE`, shifts `TRUE` to index 1 and writes
`FALSE` to index 0. Worker B read `FALSE` and `TRUE` before A's writes, so it
also inserts at index 0. It then shifts index 0, which by now holds `FALSE`, to
index 1, and writes `FALSE` to index 0. The result is `[FALSE, FALSE]`, marked
as normalized. Since `isNorm` is not volatile, a worker can also read
`isNorm = true` and skip sorting before the sorted elements are visible to it.

TLC already guards against this race for constant definitions.
`SpecProcessor` stores the value of a zero-arity constant definition through
`WorkerValue.demux` (`tool/impl/SpecProcessor.java:359`). That method normalizes
the value deeply and, with more than one worker, evaluates it once per worker
(`tool/impl/WorkerValue.java:117-141`). Its comment cites issue
[#361](https://github.com/tlaplus/tlaplus/issues/361) and records the premise
that state values can be shared because each state's values are fingerprinted
before the state is enqueued. The values bound in `Action.con` go through
neither step. When a state takes such a value, that fingerprinting is itself
the concurrent normalization.

## Corpus evidence

The `module` corpus68 run checked every input with TLC and with TLC-n, which
is TLC with 4 workers ([ADR 0018](../../docs/decisions/0018-parallel-tlc-stage.md)),
and used the recursion library of
[recursive operators](../../docs/manual/recursive-operators.md). Of about
500,000 inputs that reached the aggregator, one, `23cfd497`, was labeled
`STATE_COUNT` by the triager
([ADR 0019](../../docs/decisions/0019-state-count-agreement.md)). Both checkers
passed, but TLC reported 7 distinct states and TLC-n reported 8. The part of
the input that matters:

```tla
Init ==
  var0 \in { {{TRUE}}, {{FALSE}} } \union { {{TRUE}}, {{FALSE}} } /\ step = 0
Next ==
  ((\E actionParam1 \in {{ { TRUE, FALSE }, { TRUE, FALSE }, { TRUE, FALSE } }}:
        step < 5 /\ var0' = actionParam1 /\ step' = step + 1))
    \/ UNCHANGED (<<var0, step>>)
```

The only value of `actionParam1` is `{{TRUE, FALSE}}`, so 7 states are
reachable. TLC-n's metrics recorded a state with a set of cardinality 3. In 120
reruns with 4 workers, 1 found 8 states. A state dump of such a rerun showed
`var0 = {{FALSE, FALSE}, {FALSE, FALSE}, {FALSE, TRUE}}` in all six states with
`step` from 1 to 5. Two of them have `step = 1` and print the same value: they
are one state, fingerprinted before and after the shared object changed. The
outer set and its three inner sets were all corrupted. The input passed only because `Inv` does not
read `var0`.

## Expected behavior

TLC computes the same values with any number of workers. Either values bound
in a split action's context are normalized deeply before the workers start, as
constant definitions are, or normalization of a shared set publishes a sorted
copy instead of sorting in place, as PR #1448 does.

## Impact

Parallel TLC is the default for large models. With this defect, a model whose
next-state action takes a set-valued parameter from a constant set written in
`Next`, or computed by an operator with arguments such as `\E q \in Quorums(N)`,
can produce a spurious counterexample or a wrong state count, depending on
thread scheduling. A bound that is a zero-arity definition is normalized at
startup and is not affected. Bounds given by declared constants were not
tested. A spurious counterexample shows a value that the
specification cannot produce, so a user may look for the error in the
specification. By #1445, the same race can also drop states and hide
violations. Rerunning with `-workers 1` hides the defect, so the result looks
like a flaky model rather than a TLC fault.
