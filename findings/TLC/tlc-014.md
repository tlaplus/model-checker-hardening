# A double negation around a temporal subformula makes TLC report a spurious counterexample

## Summary

**Fixed in https://github.com/tlaplus/tlaplus/pull/1443**

`~~F` is `F`. When `F` is itself a temporal formula and the double negation
occurs *under* another temporal operator, TLC reports

```text
Error: Temporal properties were violated.
```

(exit 12) with a one-state counter-example, for properties that hold on every
behavior of the specification. The same property written without the double
negation is checked and passes. The rewriting is unsound in one direction only:
it invents violations, it does not hide them.

`~(<>(~F))` normalizes to the same shape, so the common way to write `[]F` with
`~<>~` triggers it as well.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20260917.033119-76`), tlaplus/tlaplus commit `142d0ba`; FuzzTLA
`ef6df80`. Apalache 0.62.2 (build `f0dec98`) checks the same property and
reports no error, and TLAPM `b064bce` proves it (see
[Machine-checked](#machine-checked)), so the counter-example is spurious rather
than a disagreement about semantics.

## Reproduction

`FuzzInput.tla`:

```tla
---- MODULE FuzzInput ----
EXTENDS Integers
VARIABLE x
Init == x = 0
Next == (x < 3 /\ x' = x + 1) \/ UNCHANGED x
Spec == Init /\ [][Next]_x
Prop == [](~(~([](x >= 0))))
====
```

`FuzzInput.cfg`:

```text
SPECIFICATION Spec
PROPERTY Prop
```

```sh
java -cp tla2tools.jar tlc2.TLC -deadlock -noGenerateSpecTE -config FuzzInput FuzzInput
echo $?
```

```text
Implied-temporal checking--satisfiability problem has 1 branches.
Computing initial states...
Finished computing initial states: 1 distinct state generated.
Error: Temporal properties were violated.

Error: The following behavior constitutes a counter-example:

State 1: <Initial predicate>
x = 0

12
```

`x >= 0` holds in every reachable state, so `[]([](x >= 0))` holds on every
behavior, and the single reported state satisfies it.

## Shapes

All rows use the module above, changing only `Prop`.

| `Prop` | Result |
| --- | --- |
| `[]([](x >= 0))` | checked, exit 0 |
| `~~([](x >= 0))` | checked, exit 0 |
| `[](~(~(x >= 0)))` | checked, exit 0 |
| `[](~(~([](x >= 0))))` | violated, exit 12 |
| `~(<>(~([](x >= 0))))` | violated, exit 12 |
| `<>(~(~([](x >= 0))))` | violated, exit 12 |
| `[](x >= 0 => ~(~([](x >= 0))))` | violated, exit 12 |
| `<>(~(FALSE ~> FALSE)) => FALSE` | violated, exit 12 |
| `~(<>(~(x >= 0 ~> x >= 0)))` | violated, exit 12 |

Two conditions are needed. The negated subformula must be temporal: with a
state predicate under `~~`, TLC is correct. And the double negation must sit
under a temporal operator: at the top of the property, `~~([]P)` is checked
correctly. `A => FALSE` is `~A`, which is why the `=> FALSE` row, whose
antecedent is unsatisfiable, is rejected rather than trivially true.

## Machine-checked

[`Tlc014Proofs.tla`](Tlc014Proofs.tla) proves every shape TLC reports as
violated, against the same module as the reproduction above with `P == x >= 0`:

| Theorem | Statement |
| --- | --- |
| `Corpus` | `<>(~(FALSE ~> FALSE)) => FALSE` |
| `Inert` | `([]P) <=> [](~(~([]P)))` |
| `Mwe` | `Spec => [](~(~([]P)))` |
| `Row2` | `Spec => ~(<>(~([]P)))` |
| `Row3` | `Spec => <>(~(~([]P)))` |
| `Row4` | `Spec => [](P => ~(~([]P)))` |
| `Row6` | `~(<>(~(P ~> P)))` |

```sh
tlapm --toolbox 0 0 findings/TLC/Tlc014Proofs.tla
```

```text
[INFO]: All 29 obligations proved.
```

TLAPM `b064bce` discharges the temporal steps with LS4 and the arithmetic with
Zenon, Isabelle and Z3/CVC. `Corpus` and `Row6` need no specification: they are
propositional-temporal tautologies, so TLC's counter-examples refute a formula
valid on every behavior of every module, independently of `Spec`. `Inert`
states the rewriting TLC gets wrong.

A negative control confirms the backends discriminate: `([]P) <=> [](~([]P))`,
`(<>(~(FALSE ~> FALSE)) => TRUE) => FALSE` and `Spec => [](x > 0)` each fail
with `Could not prove or check`. The single-negation variant fails while the
double-negation one is proved, which is exactly the distinction TLC loses.

## Corpus evidence

corpus35 entry `c9e9762e` is a TLC-counterexample/Apalache-pass aggregator
deviation. It is a pure PBT candidate, not a mutant: its `gen` metadata records
generation 102 and richness cohort 5, with no `parent` and no `operators`. The
generated module, with its type annotations stripped:

```tla
---- MODULE FuzzInput ----
EXTENDS Integers, Sequences, FiniteSets, TLC, Apalache, Variants
VARIABLE var0, step
Init == var0 = { [field0 |-> FALSE], [field0 |-> FALSE] } /\ step = 0
Next == ((step < 5 /\ FALSE
          /\ var0' = { [field0 |-> TRUE], [field0 |-> FALSE] }
          /\ step' = step + 1))
        \/ UNCHANGED (<<var0, step>>)
Inv  == (label1 :: ({ TRUE, FALSE } \subseteq { TRUE, FALSE }))
Fairness == TRUE
Spec == Init /\ []([Next]_(<<var0, step>>)) /\ Fairness
Prop == <>(~(FALSE ~> FALSE)) => FALSE
====
```

Everything but `Prop` is inert. The only non-stuttering disjunct of `Next` is
guarded by a literal `FALSE`, and `Inv` is a labeled tautology, so TLC records
one initial state, two distinct states, `depth: 0` and `traceLength: 0`: the
deviation needs no state exploration.

`FALSE ~> FALSE` is `[](FALSE => <>FALSE)`, a tautology, so the antecedent
`<>(~(FALSE ~> FALSE))` is `<>FALSE`, and the property is valid. TLC reports a
counterexample at the initial state and exits 12; Apalache passes.

The module contains one `~`. The second negation is TLC's own, from normalizing
`A => FALSE` into `~A` under the `[]` the normalizer introduces, which is why
the defect is reachable from properties nobody would write with an explicit
`~~`. Nothing in the generator aims at the shape either:
`BooleanExpressionKind` lists `ALWAYS`, `EVENTUALLY` and `LEADS_TO` beside `NOT`
and `IMPLIES`, so `Prop` is one draw of
`IMPLIES(EVENTUALLY(NOT(LEADS_TO(FALSE, FALSE))), FALSE)`.

It is the only instance in corpora 33 to 35. Those runs leave two, three and
three `NEW` deviations in this verdict direction; the other seven are
[order-sensitive `ApaFoldSet`](../../conformance/order-sensitive-set-fold.md).
Rerun with FuzzTLA `ef6df80`, TLC commit `142d0ba` and Apalache 0.62.2 (build
`f0dec98`).

## Expected behavior

TLC checks `~~F` exactly as it checks `F`, in every context.

## Impact

A valid property is reported as violated with a counter-example that does not
violate it. A consumer that reads the exit status records a correct
specification as refuted, and the printed behavior gives no way to see that the
report is spurious. Because `A => FALSE` and `~<>~A` are ordinary ways to write
a negation, the shape is reachable from properties nobody would write with an
explicit `~~`.
