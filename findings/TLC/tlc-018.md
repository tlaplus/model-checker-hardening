# TLC's error call stack keeps every frame evaluated after an exception it discards

## Summary

After an evaluation error, TLC replays the failing step under `CallStackTool`
to print the nested expression positions. When the replay formats the error
message, `FcnLambdaValue.toString` evaluates lazy functions and discards any
exception they raise. The discarded exception has already frozen the call
stack, so every frame that TLC evaluates afterwards stays on it. The printed
call stack grows with the evaluation work done after the discarded exception,
not with the nesting depth of the error. It can exhaust the heap of a
specification with one reachable state.

In the reproduction below, a function application outside the domain has a
call stack of 2 frames. With `N = 1000`, TLC prints 3,003 frames. With
`N = 2000000`, it prints 6,000,003 frames (418 MB) with a 4 GB heap, and with a
512 MB heap it runs out of memory after reporting the error. The third frame is
also wrong in every case: it locates the discarded exception, not the error.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20260925.164314-82`, tlaplus/tlaplus commit `8f4bc8b`), FuzzTLA
`bcfbb00`, and Apalache 0.62.2.

## Reproduction

`CallStackFreeze.tla`:

```tla
---- MODULE CallStackFreeze ----
EXTENDS Naturals, Sequences
CONSTANT N
VARIABLE x
G == [k \in {x} |-> Head(<<>>)]
H == [k \in 1..N |-> k + x]
F == [s \in {1} |-> <<G, H>>]
Init == x = 0
Next == x' = F[2]
====
```

`CallStackFreeze.cfg`:

```text
CONSTANT N = 1000
INIT Init
NEXT Next
```

```sh
java -Xmx512m -XX:+ExitOnOutOfMemoryError -cp tla2tools.jar tlc2.TLC \
  -workers 1 -noGenerateSpecTE -config CallStackFreeze CallStackFreeze
```

`2` is not in `DOMAIN F`. TLC reports this correctly, prints the one-state
behavior, and exits 75. The nested positions that follow are:

```text
Error: The error occurred when TLC was evaluating the nested
expressions at the following positions:
0. Line 9, column 9 to line 9, column 17 in CallStackFreeze
1. Line 9, column 14 to line 9, column 17 in CallStackFreeze
2. Line 5, column 21 to line 5, column 30 in CallStackFreeze
3. Line 6, column 22 to line 6, column 26 in CallStackFreeze
4. Line 6, column 22 to line 6, column 22 in CallStackFreeze
5. Line 6, column 26 to line 6, column 26 in CallStackFreeze
6. Line 6, column 22 to line 6, column 26 in CallStackFreeze
...
3002. Line 6, column 26 to line 6, column 26 in CallStackFreeze
```

Frames 0 and 1 are `Next` and `F[2]`. Frame 2 is `Head(<<>>)` in `G`, which
the error does not involve. Frames 3 to 3002 are the `N` evaluations of
`k + x` in `H`, three frames each.

| `N` | Heap | Frames | Output | Peak RSS | Exit |
|---:|---|---:|---:|---:|---:|
| 1 | 512 MB | 6 | 2.5 KB | 92 MB | 75 |
| 1,000 | 512 MB | 3,003 | 198 KB | 98 MB | 75 |
| 100,000 | 512 MB | 300,003 | 20 MB | 281 MB | 75 |
| 2,000,000 | 512 MB | – | 17 MB | 613 MB | 3, `OutOfMemoryError` |
| 2,000,000 | 4 GB | 6,000,003 | 418 MB | 3.9 GB | 75 |

With `N = 2000000` and 512 MB, the output ends after the error message and the
behavior with `Terminating due to java.lang.OutOfMemoryError: Java heap space`.
With `Next == x' = x`, TLC checks the same module in 0.3 seconds and exits 0.

`G` and `H` must depend on a variable. TLC evaluates constant definitions
once at startup, with the plain `Tool`, so their values do not evaluate through
`CallStackTool` during the replay.

## Cause

From `tlatools/org.lamport.tlatools/src` at `8f4bc8b`:

1. `ModelChecker` catches the error, prints it and the behavior, and replays
   the step with a `CallStackTool` to collect the nested positions
   ([tlc-007](tlc-007.md) describes the replay).
2. `CallStackTool.eval` and `evalAppl` push each expression and pop it in a
   `finally` block. On a `TLCRuntimeException` or `EvalException` they call
   `CallStack.freeze()`, which turns every later `pop()` into a no-op, so that
   the unwinding Java stack does not clear the positions it is about to print.
   The same methods wrap every returned `FcnLambdaValue` with the
   `CallStackTool`, so a lazy function evaluates through it later.
3. `FcnLambdaValue.apply` (`FcnLambdaValue.java:189`) formats the domain error
   as `"In applying the function\n" + Values.ppr(this.toString()) + ...`.
4. `FcnLambdaValue.toString(StringBuffer, int, boolean)`
   (`FcnLambdaValue.java:775-782`) calls `toFcnRcd()`, which evaluates the body
   for every domain element, and discards any failure with
   `catch (Throwable e) { /*SKIP*/ }`.

Formatting `F` formats `<<G, H>>`. `G`'s body raises the `Head` error, which
freezes the stack, pushes frame 2, and is discarded. Formatting `H` then pushes
three frames per element and pops none. The error that reaches `ModelChecker`
is the domain error, but the call stack it prints is the frozen one.

`CallStack.toString` skips only consecutive identical frames, so the
alternating frames of `k + x` are all printed.

## Corpus evidence

The `module` corpus54 run, with the recursion library of
[recursive operators](../../docs/manual/recursive-operators.md), has one TLC
crash with this cause, `3cf5b69b`. The TLC worker's diagnostic is only
`Terminating due to java.lang.OutOfMemoryError: Java heap space`; Apalache
passes the entry. The specification has one reachable state. Its `Next`
applies a variant, `[t \in {"Tag30"} |-> ...]`, to `{1, 2, 3}`, outside its
domain, inside nested `ApaFoldSet` and `ApaFoldSeqLeft` applications whose
combinators build further variants. A standalone rerun with a 512 MB heap
prints the error and the behavior and then runs out of memory. With 2 GB it
prints 6,196,218 frames (395 MB) and exits 75. Thread dumps during the replay
show `FcnLambdaValue.apply` formatting the message through
`tlc2.pprint.Parse`, and later `CallStack.toString`.

corpus29's `8382764e`, left unreduced in
[the corpus29 residuals](../../conformance/README.md#corpus29-residuals),
has the same diagnostic: a domain error while computing the initial states,
then an out-of-memory error with a 512 MB or a 4 GB heap.

## Expected behavior

The nested positions of an error are those of the expressions that were being
evaluated when it was raised, and their number is bounded by the evaluation
depth. Formatting an error message does not change them. For example,
`CallStackTool` could copy the stack when the first exception passes instead of
freezing it, or formatting a value for a message could evaluate with the plain
`Tool`.

## Impact

An ordinary evaluation error, reported correctly by the first pass, can turn
into an out-of-memory error, or into a report of millions of lines, depending on
how much the message formatting evaluates. A consumer that runs TLC with
`-XX:+ExitOnOutOfMemoryError` loses the error's exit status 75 and records a
crash. The third and later printed positions point at unrelated expressions
even when the report is small.
