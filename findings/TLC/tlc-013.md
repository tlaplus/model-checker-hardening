# A label on a top-level `[][A]_v` property makes TLC reject a formula it otherwise checks

## Summary

TLC checks a top-level property of the form `[][A]_v`: it treats it as an
action property and reports violations with `Action property Prop is violated`.
Putting a TLA<sup>+</sup> label on the same formula — `lbl :: [][A]_v` — changes
nothing semantically, but TLC no longer recognizes the shape and reports

```text
Error: Temporal formulas containing actions must be of forms <>[]A or []<>A.
```

(error 2214), exiting with status 255 without checking anything. The label does
not have this effect on the other action forms TLC accepts: `lbl :: <>[]A`,
`lbl :: []<>A`, `lbl :: <>[][A]_v` and `lbl :: WF_v(A)` are all checked, and a
label inside the action is fine as well. Only the labeled `[][A]_v` falls
through.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20260917.033119-76`), tlaplus/tlaplus commit `142d0ba`; FuzzTLA `fe50088`;
Apalache 0.62.2 (build `f0dec98`), which is not involved in the rejection.

## Reproduction

`FuzzInput.tla`:

```tla
---- MODULE FuzzInput ----
EXTENDS Integers
VARIABLE x
Init == x = 0
Next == x < 3 /\ x' = x + 1
Spec == Init /\ [][Next]_x
Prop == lbl :: [][x' >= x]_x
====
```

`FuzzInput.cfg`:

```text
SPECIFICATION Spec
PROPERTY Prop
```

```sh
java -cp tla2tools.jar tlc2.TLC -deadlock -noGenerateSpecTE -config FuzzInput FuzzInput
echo $?
```

```text
Starting... (2026-09-20 03:26:52)
Error: Temporal formulas containing actions must be of forms <>[]A or []<>A.
Finished in 00s at (2026-09-20 03:26:52)
255
```

Removing the label, TLC explores the four-state graph and passes. The label's
effect by shape, all with the same module skeleton:

| `Prop` | Result |
| --- | --- |
| `[][x' >= x]_x` | checked, exit 0 |
| `[][x' = x + 2]_x` | checked, `Action property Prop is violated`, exit 13 |
| `lbl :: [][x' >= x]_x` | error 2214, exit 255 |
| `lbl :: lbl2 :: [][x' >= x]_x` | error 2214, exit 255 |
| `lbl :: [][Next]_x` | error 2214, exit 255 |
| `lbl :: <>(x = 3)` | checked, exit 13 |
| `lbl :: []<>(x = 3)` | checked, exit 13 |
| `lbl :: <>[][x' >= x]_x` | checked, exit 0 |
| `lbl :: WF_x(Next)` | checked, exit 13 |
| `[][lbl :: (x' >= x)]_x` | checked, exit 0 |

The unlabeled `[][A]_v` under `<>`, `~>`, `[]`, a connective or an `IF` branch
is rejected with the same message; those shapes are covered by
[tlc-temporal-formula-limits](../../conformance/tlc-temporal-formula-limits.md),
which also lists the labeled row this finding promotes. The defect is the
asymmetry: a label is only a name for a subexpression, yet it decides whether
TLC checks the property or rejects it.

## Corpus evidence

The `module` corpus32 run has five TLC crashes with this cause, triaged as NEW
because no known-defect signature matches them:

- `5129bc6b`: `Prop == label14 :: ([][(...)]_FALSE)`, where the action is a
  fold over `{TRUE, FALSE}`;
- `a262ea47`: `Prop == label14 :: (label15 :: ([][(...) <= step]_FALSE))`;
- `b9b7e619`: `Prop == label34 :: ([][(<<[FALSE]_(...))>>_FALSE]_FALSE)`;
- `bc14b373`: `Prop == label13 :: ([][(VariantGetOrElse(...))]_FALSE)`;
- `c6231474`: `Prop == label10 :: ([][((FALSE /= FALSE)')]_FALSE)`.

All five print the `must be of forms` message and exit 255. The
[signature matcher](../../docs/manual/known-defect-signatures.md) skips labels,
so a pattern that matches these also matches the unlabeled `[][A]_v`, which TLC
checks; the shape cannot be quarantined without losing that coverage.

The `module` corpus33 run has 12 more, again all triaged as NEW, each a label
directly on `[][A]_v` with the subscript `FALSE` or `var0`, for example
`0130d26e`: `Prop == label4 :: ([][(step < step)]_FALSE)` and `9946e76e`:
`Prop == label3 :: ([][(~(label4 :: FALSE))]_var0)`. The other ten are
`00558e74`, `13bd54fb`, `175da01d`, `271ad339`, `2916735a`, `51dd2c9d`,
`a14ce059`, `cb4f22dd`, `dd513031` and `f4a8f8c2`. Reclassified with FuzzTLA
`d4f274c` and TLC commit `142d0ba` (tla2tools `1.8.0-20260917.033119-76`).

The `module` corpus35 run has 13 more, all `NEW` for the same reason, each a
label directly on `[][A]_v` with the subscript `FALSE`, `var1` or a `Variant`
value, for example `03aeba66`: `Prop == label8 :: ([][(FALSE)]_FALSE)`,
`07abcdd8`: `Prop == label2 :: ([][var0]_FALSE)` and `7a1faf38`, whose property
carries two nested labels. The other ten are `0fb62e86`, `1cb55221`,
`635b2363`, `867c8494`, `8c39f07f`, `ac78368a`, `bef936bf`, `dbcf54c0`,
`e3b95ab3` and `e69a3de3`. Reclassified with FuzzTLA `ef6df80` and TLC commit
`142d0ba` (tla2tools `1.8.0-20260917.033119-76`).

## Expected behavior

TLC checks `lbl :: [][A]_v` exactly as it checks `[][A]_v`.

## Impact

A well-formed property that TLC can check is rejected, and the rejection cannot
be quarantined by a known-defect signature, so every corpus run that generates a
labeled `[][A]_v` property records a spurious TLC crash.
