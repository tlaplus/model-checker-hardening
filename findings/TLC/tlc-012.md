# `ENABLED UNCHANGED e` fails with a `WF_v(A)` message when `e` is not a variable or tuple

## Summary

TLC cannot evaluate `ENABLED UNCHANGED e` when `e` is an expression over state
variables other than a variable, a tuple or a zero-arity definition, such as
`x + 1` or `<<x>>[1]`. The formula is well defined: it equals `ENABLED (e' = e)`,
and `x' = x` satisfies it. TLC reports

```text
The action formula A appearing in a WF_v(A) or SF_v(A) operator does not specify the primed value of the variable x occurring in the state formula v.
```

and exits 75. The specification need not contain `WF` or `SF`, so the message
names operators the user did not write.

The cause is in `Tool.enabledUnchangedImpl`. Variables, tuples and zero-arity
definitions are handled structurally. Any other expression is evaluated as
`e'` in the partial successor state, with `EvalControl.Primed`. When a variable
of `e` is not yet bound, the primed lookup raises
`TLC_STATE_NOT_COMPLETELY_SPECIFIED_LIVE` (2148), whose text is the fairness
message above. A comment at that call already calls this path buggy, with the
reproduction `ENABLED (UNCHANGED op(t))`. It records a different message, "In
evaluation, the identifier t is either undefined or not an operator".

The result depends on conjunct order. `ENABLED (x' = x /\ UNCHANGED (x + 1))`
binds `x'` first and passes, while `ENABLED (UNCHANGED (x + 1) /\ x' = x)` fails.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20260915.155503-70`), the TLC bundled in FuzzTLA on 2026-09-15. The source
cited is `tlaplus/tlaplus` at `8585374d`.

## Reproduction

`FuzzInput.tla`:

```tla
---- MODULE FuzzInput ----
EXTENDS Integers
VARIABLE x
Init == x = 0
Next == UNCHANGED x
Inv == ENABLED UNCHANGED (x + 1)
====
```

`FuzzInput.cfg`:

```text
INIT Init
NEXT Next
INVARIANT Inv
```

```sh
java -cp tla2tools.jar tlc2.TLC -deadlock -noGenerateSpecTE -config FuzzInput FuzzInput
echo $?
```

Replacing `Inv`:

| `Inv` | Result |
| --- | --- |
| `ENABLED UNCHANGED (x + 1)` | `WF_v(A)` message, exit 75 |
| `ENABLED UNCHANGED <<x>>[1]` | `WF_v(A)` message, exit 75 |
| `ENABLED UNCHANGED (IF TRUE THEN x ELSE x)` | `WF_v(A)` message, exit 75 |
| `ENABLED (UNCHANGED (x + 1) /\ x' = x)` | `WF_v(A)` message, exit 75 |
| `ENABLED (x' = x /\ UNCHANGED (x + 1))` | no error |
| `ENABLED UNCHANGED <<x, x + 1>>` | no error, the tuple binds `x'` first |
| `ENABLED UNCHANGED x` | no error |
| `ENABLED ((x + 1)' = x + 1)` | "In evaluation, the identifier x is either undefined or not an operator", exit 75 |

The same message for an actual `WF_v(A)` whose action leaves a variable of `v`
unprimed is expected. That case is reported as error 1000 while TLC checks liveness,
and [tlc-010](tlc-010.md) covers it.

## Corpus evidence

The `module` corpus24 run has two aggregator deviations with this cause. In
both, TLC fails with exit 75 and the stored detail
`The action formula A appearing in a WF_v(A) or SF_v(A) operator does not specif…`.
Neither specification contains `WF` or `SF`:

- `d65d9c03`: the invariant contains
  `CASE ENABLED (UNCHANGED ((LET ... IN ApaFoldSet(...))["field29"])) -> ...`.
  Apalache passes, because the `ENABLED` is the guard of a `CASE` without `OTHER`
  ([apalache-bmc-019](../apalache-bmc/apalache-bmc-019.md)).
- `7fd26b9f`: `Inv == IF (CASE ENABLED (UNCHANGED (IF CHOOSE bound1 \in ...)) ...`.
  Apalache reports a counterexample. That verdict was not examined further.

The four earlier TLC crashes with this message, two in corpus23 and two in
corpus24, are all actual `WF` or `SF` formulas and remain
[tlc-010](tlc-010.md).

## Expected behavior

TLC evaluates `ENABLED UNCHANGED e` as `ENABLED (e' = e)`, binding the unbound
variables of `e` as it does for a tuple of variables. If it cannot, it names
`ENABLED` and `UNCHANGED` in its message rather than `WF_v(A)` or `SF_v(A)`.

## Impact

A correct invariant fails, and the message points the user to fairness
conditions that the specification does not contain. Automated consumers record a
spurious TLC failure.
