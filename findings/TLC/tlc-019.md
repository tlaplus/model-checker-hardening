# A stack overflow while TLC reconstructs a liveness counterexample ends the JVM with `System.exit(1)`

## Summary

When TLC finds a liveness violation, it reconstructs the prefix of the
counterexample in a separate thread. If that thread throws a
`StackOverflowError`, TLC prints "TLC threw an unexpected exception" with
`java.util.concurrent.ExecutionException: java.lang.StackOverflowError` and
calls `System.exit(1)` from `LiveCheck`. `TLC.process()` never returns. Exit
status 1 is not one of TLC's exit codes, and the message is not TLC's
stack-overflow diagnostic, which `LiveCheck` has a branch for but does not
reach. An application that runs TLC in its own JVM is terminated with it.

The reconstruction re-evaluates `Next` and can need more stack than the
exploration that found the same states. With the JIT enabled, a specification
whose states TLC explores successfully can therefore fail only while its
counterexample is printed. Safety counterexamples of the same specification are
reconstructed without this failure.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20261013.012418-104`, tlaplus/tlaplus commit `210df3a`), FuzzTLA
`bf5678c`, and Apalache 0.62.3 (`3eb15b2`), on OpenJDK 25.0.4.1 for Linux
aarch64. [tlc-performance-001](../tlc-performance/tlc-performance-001.md)
describes the stack use of the recursion itself; this finding is about how TLC
handles the overflow on the liveness path.

## Reproduction

`PrefixOverflow.tla`:

```tla
---- MODULE PrefixOverflow ----
EXTENDS Naturals, Sequences
RECURSIVE Double(_)
Double(s) == IF s = <<>> THEN <<>> ELSE <<2 * Head(s)>> \o Double(Tail(s))
VARIABLES x, n
Init == x = <<1>> /\ n = 0
Next == \/ n < 5 /\ x' = Double(x) \o <<1, 2, 3>> \o x \o <<1, 2, 3>> /\ n' = n + 1
        \/ UNCHANGED <<x, n>>
Spec == Init /\ [][Next]_<<x, n>>
Live == <>FALSE
====
```

`PrefixOverflow.cfg`:

```text
SPECIFICATION Spec
PROPERTY Live
```

The JVM options are those FuzzTLA passes to its TLC workers, with a small
stack:

```sh
java -Xss384k -XX:TieredStopAtLevel=1 -XX:ActiveProcessorCount=1 \
  -cp tla2tools.jar tlc2.TLC -workers 1 -deadlock -noGenerateSpecTE \
  -config PrefixOverflow PrefixOverflow
echo $?
```

```text
Implied-temporal checking--satisfiability problem has 1 branches.
Computing initial states...
Finished computing initial states: 1 distinct state generated at 2026-10-16 03:56:05.
Progress(6) at 2026-10-16 03:56:05: 12 states generated, 6 distinct states found, 0 states left on queue.
Checking temporal properties for the complete state space with 6 total distinct states at (2026-10-16 03:56:05)
Error: TLC threw an unexpected exception.
This was probably caused by an error in the spec or model.
See the User Output or TLC Console for clues to what happened.
The exception was a java.util.concurrent.ExecutionException

```

The last sequence has 218 elements. Exploration completes, and the failure
happens after "Checking temporal properties". Exit statuses of three runs per
stack size, with the same options:

| `-Xss` | `PROPERTY Live` | `INVARIANT n < 5` |
| --- | --- | --- |
| 320k | 255, 255, 255 (overflow during exploration) | 255 |
| 384k | 1, 1, 1 | 12 |
| 448k | 13, 1, 1 | 12 |
| 512k | 1, 1, 13 | 12 |
| 640k | 1, 13, 13 | – |
| 768k, 1m | 13, 13, 13 | – |

Exit 255 with "This was a Java StackOverflowError" is the overflow reported
correctly during exploration ([tlc-performance-001](../tlc-performance/tlc-performance-001.md)).
Exit 13 is the expected liveness violation. Between them, the outcome depends
on JIT timing. With `-Xint`, exploration and reconstruction overflow at the same
stack size, 320k, and both properties are checked from 384k on, so the
additional stack the reconstruction needs comes from compilation state, not
from deeper evaluation. Without `-XX:ActiveProcessorCount=1` and with the
default tiered compilation, the window shifts but remains.

## Cause

From `tlatools/org.lamport.tlatools/src/tlc2/tool/liveness` at `210df3a`:

1. `LiveWorker.printTrace` (`LiveWorker.java:836-870`) submits the prefix
   reconstruction to a new single-thread executor. The task calls
   `ITool.getState(fp, sinfo)` for each state of the prefix, which re-evaluates
   `Next` to find the successor with that fingerprint.
2. `printTrace` waits with `future.get()` (`LiveWorker.java:927-937`). It
   unwraps the `ExecutionException` only when its cause is an `EvalException`
   and otherwise rethrows it, so a `StackOverflowError` leaves `printTrace`
   wrapped in an `ExecutionException`.
3. `LiveCheck.check0` runs the `LiveWorker` in another executor and receives an
   `ExecutionException` whose cause is that `ExecutionException`
   (`LiveCheck.java:304-331`). It reports `EC.SYSTEM_OUT_OF_MEMORY_LIVENESS` or
   `EC.SYSTEM_STACK_OVERFLOW` only when the direct cause is an
   `OutOfMemoryError` or a `StackOverflowError`. Here it is not, so it reports
   `EC.GENERAL` with the inner exception and then calls `System.exit(1)` for
   every failure.

A JVM that runs out of memory during reconstruction takes the same path.

## Corpus evidence

The `module` corpus64 run, with the recursion library of
[recursive operators](../../docs/manual/recursive-operators.md) and TLC as the
only checker, has two TLC crashes of this kind, `4c8676fa` and `d301ca55`. Both
are single-byte mutants of entries in `04quality-pass`, and in both the mutation
replaced a fold in `Next` with a recursion over the growing state variable:
`SeqMapDouble(var0)` in `4c8676fa`, whose sequence grows to 218 elements in five
steps, and `SeqFilterPositive(SeqMapDouble(var0))` in `d301ca55`, whose sequence
grows to 125 elements. In both, `Prop` is violated. The TLC worker
diagnostic was only "TLC worker exited while processing the input": the worker
runs TLC in-process and buffers its output, so `System.exit(1)` discarded both
the verdict and the output. FuzzTLA now prints the buffered output of an
unfinished input to the worker's standard error from a shutdown hook.

corpus64 ran on Linux amd64, whose default thread stack is 1 MB. On the aarch64
machine above, whose default is 2 MB, both entries report the violation and
exit 13 in all of 30 runs. With `-Xss512k` and FuzzTLA's options, they exit 1 in
3 of 3 runs. `4c8676fa` needs about 896 KB to report the violation, while 384 KB
suffice to explore its states. Rerun through FuzzTLA with
`JAVA_TOOL_OPTIONS=-Xss512k`, both crash with the corpus diagnostic.

## Expected behavior

`TLC.process()` returns an error code, as it does for a stack overflow during
exploration, and TLC prints its stack-overflow diagnostic. The prefix
reconstruction could unwrap any `ExecutionException` cause, or `LiveCheck`
could inspect the innermost cause before choosing the message, and return an
error code instead of exiting.

## Impact

An application that embeds TLC, such as a test harness, an IDE or a service,
loses its JVM, and with it any output that it has not yet written. A user of
the command line sees a generic "unexpected exception" message and exit status
1 instead of the stack-overflow advice to increase `-Xss`. Since the
reconstruction can need more stack than the exploration, a model that TLC
explores successfully can still fail when it reports its counterexample, and
whether it does depends on the JVM, the architecture and JIT timing.
