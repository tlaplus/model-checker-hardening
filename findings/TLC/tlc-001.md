# Function-domain errors inside set filters escape as TLC error 1000

## Summary

TLC normally reports a function application outside its domain as evaluation
error 2103. When the same error occurs while evaluating a set-filter predicate,
it escapes as an unexpected `RuntimeException`; TLC reports general error 1000
and exits with status 255.

The `corpus4` instance reproduced twice with both the recorded TLC build and the
current bundled snapshot.
See the [`ebba0a38...` input](../../corpus4/02tlc-crash/ebba0a3853bb62125b3182a12d473ede46ad493250c5d544e300949f429afcd1.cbor)
and its [stacktrace](../../corpus4/02tlc-crash/ebba0a3853bb62125b3182a12d473ede46ad493250c5d544e300949f429afcd1.stacktrace).

## Reproduction

```tla
---- MODULE FilterDomainError ----

VARIABLE value

Init == value = UNION ({s \in SUBSET ({}):
  ([[i \in {} |-> FALSE] EXCEPT !["missing"] = FALSE])["missing"]
})
Next == UNCHANGED value
Inv == TRUE

====
```

TLC reports:

```text
TLC error code 1000 mapped to exit status 255
Error: TLC threw an unexpected exception.
The exception was a java.lang.RuntimeException:
In applying the function <<>>, the first argument is "missing",
which is not in its domain.
```

Removing the surrounding set filter makes TLC report the same missing-domain
application as ordinary error 2103 and exit status 75.

## Expected behavior and impact

Evaluation inside a set-filter predicate must preserve TLC's ordinary
specification-error classification. The filter evaluator should propagate the
structured evaluation error instead of wrapping it in a generic runtime
exception.

The status-255 result causes automated consumers to retain an undefined input
as a TLC crash even though the underlying semantic error is already known and
classified elsewhere.
