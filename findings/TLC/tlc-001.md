# An evaluation error in a lazy initial-state value escapes as TLC error 1000

## Summary

When fingerprinting an initial state forces a lazy value, such as a set filter
under `UNION` or a function whose domain TLC does not enumerate eagerly, and
the evaluation fails with a `TLCRuntimeException`, TLC reports general error
1000, prints "TLC threw an unexpected exception", and exits with status 255.
The underlying diagnostic, for example a function application outside its
domain or a `CHOOSE` without a witness, is quoted inside the wrapper. TLC
prints no error call stack.

The error escapes from TLC's own error handler. `ModelChecker` records the
failing initial state and then prints it with `TLCStateMut.toString()`.
Printing normalizes the state's values again, forces the same lazy value, and
rethrows the same exception from inside the `catch` block. See
[Root cause](#root-cause). The same root cause also produces the error-1000
crashes of [`tlc-003`](tlc-003.md).

Observed with the TLC snapshot bundled in FuzzTLA, TLC commit `94d0c50`
(tla2tools `1.8.0-20261006.015956-102`).

## Reproduction

```tla
---- MODULE FilterDomainError ----

VARIABLE value

Init == value = UNION ({s \in SUBSET ({}):
  ([[i \in {} |-> FALSE] EXCEPT !["missing"] = FALSE])["missing"]
})
Next == UNCHANGED value
Inv == TRUE

====
```

TLC reports:

```text
TLC error code 1000 mapped to exit status 255
Error: TLC threw an unexpected exception.
The exception was a java.lang.RuntimeException:
In applying the function <<>>, the first argument is "missing",
which is not in its domain.
```

The filter is not essential. A set of two lazy functions fails the same way,
here with a `CHOOSE` without a witness (`corpus59` entry `a96cc07a`):

```tla
---- MODULE LazyFunctionChoose ----
VARIABLE x
Init == x = {[e \in SUBSET {1} |-> CHOOSE c \in {} : TRUE],
             [e \in SUBSET {1} |-> 1]}
Next == UNCHANGED x
====
```

```text
Error: TLC threw an unexpected exception.
This was probably caused by an error in the spec or model.
See the User Output or TLC Console for clues to what happened.
The exception was a java.lang.RuntimeException
: Attempted to compute the value of an expression of form
CHOOSE x \in S: P, but no element of S satisfied P.
line 3, col 36 to line 3, col 57 of module LazyFunctionChoose
```

Each of the following changes makes TLC report the ordinary error, with an
error call stack, and exit 75:

| Change to `LazyFunctionChoose` | Why the escape disappears |
| --- | --- |
| domain `{1}` or `1..2` instead of `SUBSET {1}` | the domain is `Reducible`, so `Tool` converts the function to a record while it evaluates `Init` |
| the second function removed | not traced; the call-stack replay runs and reports the fingerprinting error |
| `Head(<<>>)` or `1 \div 0` instead of the `CHOOSE` | the error is an `EvalException`, for which `doInit` does not record the error state |

Command:

```sh
java -Xmx512m -cp tla2tools.jar tlc2.TLC -workers 1 -deadlock -noGenerateSpecTE -nowarning LazyFunctionChoose
```

## Root cause

Line numbers are from TLC commit `94d0c50`.

1. `Tool.evalApplImpl` keeps a function constructor lazy (`FcnLambdaValue`)
   unless its domain is `Reducible`; `SUBSET {1}` is not. Set filters under
   `UNION` are lazy as well (`UnionValue` over a `SetPredValue`).
2. `ModelChecker$DoInitFunctor.addElement` fingerprints the initial state
   (`ModelChecker.java:1179`). `SetEnumValue.fingerPrint` sorts the set,
   `FcnRcdValue.compareTo` calls `FcnLambdaValue.toFcnRcd`, and the body
   raises `Assert.fail`, a `TLCDetailedRuntimeException` with error code
   `EC.GENERAL`.
3. `addElement` records the state in `errState` and rethrows. `doInit` copies
   it to `this.errState` only for `Assert.TLCRuntimeException`
   (`ModelChecker.java:388`). An `EvalException` leaves it `null`.
4. The handler in `modelCheckImpl` (`ModelChecker.java:162`) sees a non-null
   `errState` and prints `TLC_INITIAL_STATE` with `this.errState.toString()`
   (`ModelChecker.java:193`). `TLCStateMut.toString` calls
   `SetEnumValue.toString` or `UnionValue.toString`, which normalize again and
   reach the same failing evaluation.
5. That second exception is thrown inside the `catch` block. The call-stack
   replay at `ModelChecker.java:205` never runs. The exception leaves
   `modelCheck()` and reaches the catch-all in `TLC.process`
   (`TLC.java:1464`), which prints the wrapper and returns `EC.GENERAL`.

A JDWP breakpoint on `Assert.fail` confirms the two raises for
`LazyFunctionChoose`, for `FilterDomainError`, and for both `tlc-003`
reproductions. The first is under `TLCStateMut.fingerPrint` in `addElement`.
The second is under `TLCStateMut.toString` at `ModelChecker.java:193`.

## Corpus history

The `corpus1` run contains eight aggregator deviations where the same
function-domain error escapes as `java.lang.RuntimeException`, reported as
"TLC threw an unexpected exception" with the underlying message quoted in the
exception text:

```text
Error: TLC threw an unexpected exception.
The exception was a java.lang.RuntimeException
: In applying the function
<<>>,
the first argument is:
0
which is not in its domain.
```

There it is reported under error 2103 and the spec-evaluation status 75, so it
is stored as a failure rather than as a crash. The specific diagnostic is lost
inside the same generic wrapper; only the error constant it is finally
reported under differs. Those runs were not traced against the root cause
above.

Corpus8 shows the same wrapper across more diagnostics. Replaying its 1,046
unclassified aggregator deviations, 156 report `TLC threw an unexpected
exception` with the specific diagnostic quoted inside a
`java.lang.RuntimeException`: a function-domain error (57), `CHOOSE` without a
witness (53), an unmatched `CASE` (38), a non-enumerable quantifier bound (3)
and five others. All are reported under error 2103 and status 75, so they are
stored as failures. The wrapper also defeats triage: the stored detail keeps
only the first `Error:` line, which is the wrapper text, so the class of the
underlying failure is lost.

The `corpus4` instance reproduced twice with both the recorded TLC build and
the then-bundled snapshot. The `corpus42` entry `3e2b8922` and the `corpus59`
entry `a96cc07a` reach the escape with a `CHOOSE` without a witness inside a
lazy function in a set of tuples; in `a96cc07a` the `CHOOSE` is also a lazy
argument of `VariantGetOrElse`. Both raise the error under
`FcnRcdValue.compareTo` while `SetEnumValue.normalize` sorts the set.

Reproduced with FuzzTLA commit `be3d86f` and TLC commit `94d0c50`
(tla2tools `1.8.0-20261006.015956-102`), bundled in FuzzTLA, with OpenJDK
25.0.4.1 on Linux aarch64. Apalache was not rerun; it does not take part in
this crash classification.

## Expected behavior

TLC should report the original evaluation error with its ordinary
classification, exit 75, and print the error call stack. Printing the error
state must not re-evaluate values that may fail. Possible fixes are to format
the state defensively in the handler, falling back to the unnormalized
values, or to record the error state for `EvalException` and
`TLCRuntimeException` alike and print it after the call-stack replay.

## Impact

The status-255 result causes automated consumers to retain an undefined input
as a TLC crash even though the underlying semantic error is already known and
classified elsewhere. Users lose the error call stack and the initial state
that TLC meant to print.
