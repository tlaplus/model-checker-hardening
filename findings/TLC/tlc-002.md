# Diagnosed evaluation errors exit with generic status 255

## Summary

TLC diagnoses an evaluation error correctly wherever it occurs, but reports it
under a different error constant depending on where it occurs, and only some of
those constants map to an exit status that names an evaluation failure. Every
`TLC_MODULE_*` constant raised by an operator in a standard module is absent
from `EC.ExitStatus.errorConstantToExitStatus`, so TLC exits with the generic
status 255. The same failure diagnosed under `TLC_NESTED_EXPRESSION` (2103)
exits 75, and under `TLC_INVARIANT_EVALUATION_FAILED` (2111) exits 76.

Consumers therefore record an ordinary negative specification as a checker
crash, and the classification depends on which part of the specification
contains the error rather than on what the error is.

The `corpus9` run contains 274 instances under six unmapped constants, and
the `corpus14` run 163 under five of them:

| Constant | Diagnostic | corpus9 | corpus14 |
| --- | --- | ---: | ---: |
| 2184 `TLC_MODULE_APPLY_EMPTY_SEQ` | `Attempted to apply Head to the empty sequence.` | 200 | 126 |
| 2179 `TLC_MODULE_DIVISION_BY_ZERO` | `The second argument of \div is 0.` | 22 | 6 |
| 2183 `TLC_MODULE_ARGUMENT_NOT_IN_DOMAIN` | `The second argument of SubSeq must be in the domain of its first argument:` | 20 | 14 |
| 2169 `TLC_MODULE_ARGUMENT_ERROR` | `The second argument of % should be a positive number` | 17 | 7 |
| 2180 `TLC_MODULE_NULL_POWER_NULL` | `0^0 is undefined.` | 14 | 10 |
| 2178 `TLC_MODULE_OVERFLOW` | `Overflow when computing -57^6` | 1 | 0 |

The `corpus12` run adds a further diagnostic under 2169,
`The second argument of ^ should be a natural number, but instead it is: -1`,
raised by a negative exponent in the next-state relation. It exits 255 like the
others.

The 2178 instance is the only one whose error is reported while evaluating an
invariant rather than the next-state relation. Its invariant is
`IsFiniteSet({(-57) ^ step})`, so the overflow is raised inside a TLC module
override: TLC prints `Evaluating invariant Inv failed.` and still exits 255
under the module constant instead of the invariant constant 2111, which exits
76. See the [`f42d0f30...` input](../../corpus9/02tlc-crash/f42d0f30d9fd8cd7bd79c718398aa045977d3cbe9b35e18b3feb84fa48266998.cbor)
and its [stacktrace](../../corpus9/02tlc-crash/f42d0f30d9fd8cd7bd79c718398aa045977d3cbe9b35e18b3feb84fa48266998.stacktrace).
It was produced with snapshot 2026.09.08.204828; the reproductions below were
rerun with snapshot 2026.09.09.074748.

## Reproduction

The same expression changes exit status with its position. With

```tla
---- MODULE FuzzInput ----
EXTENDS Integers, Sequences, FiniteSets, TLC, Apalache, Variants

VARIABLE
  \* @type: Int;
  var0

VARIABLE
  \* @type: Int;
  step

Init == var0 = 0 /\ step = 0
Next == var0' = Head(<<>>) /\ step' = step + 1
Inv == var0 >= 0
Bound == step <= 5
====
```

and `INIT Init`, `NEXT Next`, `INVARIANT Inv`, `CONSTRAINT Bound`, TLC reports:

```text
TLC error code 2184 mapped to exit status 255
Error: Attempted to apply Head to the empty sequence.
Error: The behavior up to this point is:
```

Moving the same application into the initial predicate, so that `Init` reads
`var0 = Head(<<>>) /\ step = 0` and `Next` reads `var0' = var0 /\ step' = step + 1`,
reports the identical diagnosis under a classified status:

```text
TLC error code 2103 mapped to exit status 75
Error: Attempted to apply Head to the empty sequence.
```

Arithmetic overflow behaves the same way. With `Next` reading
`step' = step + 1 /\ (-57)^6 >= 0`:

```text
Error: Overflow when computing -57^6
Error: The behavior up to this point is:
...
TLC error code 2178 mapped to exit status 255
```

and with the same conjunct in `Init`:

```text
Error: Overflow when computing -57^6
TLC error code 2103 mapped to exit status 75
```

The invariant position reaches either constant, depending on whether the
failing operator is a module override. With `Inv == IF step = 0 THEN TRUE ELSE
(-57)^6 >= 0` the overflow is caught by the invariant path:

```text
Error: Evaluating invariant Inv failed.
Overflow when computing -57^6
TLC error code 2111 mapped to exit status 76
```

The `corpus9` invariant raises the same overflow inside `IsFiniteSet`, and the
module constant survives:

```text
Error: Evaluating invariant Inv failed.
Overflow when computing -57^6
...
TLC error code 2178 mapped to exit status 255
```

reproduced with `Inv == IsFiniteSet({(-57) ^ step})` and the same `Next` and
`Bound`. Whether a diagnosed evaluation error is reported as a checker crash
therefore depends on the operator that raises it, not on the error.

## Expected behavior

An evaluation error should reach the same exit status wherever it occurs. Every
`TLC_MODULE_*` constant describes a specification-evaluation failure and should
map to `FAILURE_SPEC_EVAL`, as 2103 already does.

## Impact

The generic status conflates an expected negative specification with a checker
crash, so an automated consumer stores these runs as crashes and they are
excluded from verdict comparison. The affected specifications are exactly those
whose evaluation error lies outside the initial predicate, which is where most
of the behavior of a non-trivial specification lives.

Working around it requires an operation-specific allowlist of error constants
that exit 255, which is incomplete by construction: 2184 was found only after a
workflow began generating specifications with a non-trivial next-state relation,
and 2178 only after one began generating invariants that can overflow.
