# Evaluation errors in the next-state relation exit with generic status 255

## Summary

TLC diagnoses an undefined operator application correctly wherever it occurs,
but reports it under a different error constant depending on where it occurs,
and only one of the two maps to an exit status that names an evaluation
failure. Applying `Head` to the empty sequence in the initial predicate is
error 2103 (`TLC_NESTED_EXPRESSION`) and exits 75. The same application in the
next-state relation is error 2184 (`TLC_MODULE_APPLY_EMPTY_SEQ`), which
`EC.ExitStatus.errorConstantToExitStatus` does not map, so TLC exits with the
generic status 255.

Consumers therefore record an ordinary negative specification as a checker
crash, and the classification depends on which part of the specification
contains the error rather than on what the error is.

Observed with the bundled TLC snapshot, version 2026.09.04. The `corpus1` run
contains two instances. See the
[`190d5a7b...` input](../../corpus1/02tlc-crash/190d5a7b82df73c73409e7579fbaf24e9b7d497ecd2fdf98a12fd84a16f19bff.cbor)
and its [stacktrace](../../corpus1/02tlc-crash/190d5a7b82df73c73409e7579fbaf24e9b7d497ecd2fdf98a12fd84a16f19bff.stacktrace).

## Reproduction

```tla
---- MODULE FuzzInput ----
EXTENDS Integers, Sequences, FiniteSets, TLC, Apalache, Variants

VARIABLE
  \* @type: Int;
  var0

VARIABLE
  \* @type: Int;
  step

Init == var0 = 0 /\ step = 0
Next == var0' = Head(<<>>) /\ step' = step + 1
Inv == var0 >= 0
Bound == step <= 5
====
```

with `INIT Init`, `NEXT Next`, `INVARIANT Inv`, `CONSTRAINT Bound` reports:

```text
TLC error code 2184 mapped to exit status 255
Error: Attempted to apply Head to the empty sequence.
Error: The behavior up to this point is:
```

Moving the same application into the initial predicate, so that `Init` reads
`var0 = Head(<<>>) /\ step = 0` and `Next` reads `var0' = var0 /\ step' = step + 1`,
reports the identical diagnosis under a classified status:

```text
TLC error code 2103 mapped to exit status 75
Error: Attempted to apply Head to the empty sequence.
```

## Expected behavior

An evaluation error should reach the same exit status wherever it occurs.
Error 2184 describes a specification-evaluation failure and should map to
`FAILURE_SPEC_EVAL`, as 2103 already does.

## Impact

The generic status conflates an expected negative specification with a checker
crash, so an automated consumer stores these runs as crashes and they are
excluded from verdict comparison. The affected specifications are exactly those
whose evaluation error lies in the next-state relation, which is where most of
the behavior of a non-trivial specification lives.

Working around it requires an operation-specific allowlist of error constants
that exit 255, which is incomplete by construction: this instance was found only
after a workflow began generating specifications with a non-trivial next-state
relation.
