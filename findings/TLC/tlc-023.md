# TLC rejects `[](F /\ G)` for fairness formulas `F` and `G` but checks `[]F /\ []G`

## Summary

TLC checks `[]WF_x(A) /\ []WF_x(B)`, but rejects the equivalent
`[](WF_x(A) /\ WF_x(B))` with

```text
Error: Temporal formulas containing actions must be of forms <>[]A or []<>A.
```

(error 2214) and exits with status 255. A bounded `\A` over a constant set
of two or more elements is expanded into the same conjunction, so
`[](\A q \in {1, 2}: WF_x(A))` is rejected while `\A q \in {1, 2}: []WF_x(A)`
and the singleton `[](\A q \in {1}: WF_x(A))` are checked. The defect is not
specific to fairness: `[]([]<><<A>>_x /\ []<><<A>>_x)`,
`[](WF_x(A) /\ x \in S)` and `<>(<>[]P \/ <>[][A]_x)` are rejected too, while
their distributed forms are checked.

`[]` distributes over `/\` and `<>` over `\/`, so every rejected property
equals one that TLC accepts. TLC does not apply this rewrite before it
classifies the conjuncts of the negated property.

Observed with TLC `bc1b506` (TLC2 version 2026.11.15.002146), FuzzTLA
`89796b2d` and Apalache 0.63.0, which reports fairness as unsupported and is
not involved.

## Reproduction

`BoxFairConj.tla`:

```tla
---- MODULE BoxFairConj ----
EXTENDS Integers
VARIABLE x
Next == x' = 1 - x
Spec == x = 0 /\ [][Next]_x /\ WF_x(Next)
Prop == [](WF_x(Next) /\ WF_x(Next))
====
```

`BoxFairConj.cfg`:

```text
SPECIFICATION Spec
PROPERTY Prop
```

```sh
java -cp tla2tools.jar tlc2.TLC -noGenerateSpecTE -config BoxFairConj.cfg BoxFairConj.tla
echo $?
```

## Root cause

The source cited is `tlaplus/tlaplus` at `bc1b506`, in
`tlc2.tool.liveness`. `Liveness.processLiveness` negates the property and
normalizes it with `pushNeg(false).simplify().toDNF()`. It then classifies each
conjunct of each disjunct with `classifyExpr`, which accepts an action only as
`<>[]A` or `[]<>A` and otherwise fails with `TLC_LIVE_WRONG_FORMULA_FORMAT`.

`WF_x(A)` translates to `[]<>(~ENABLED <<A>>_x \/ <<A>>_x)`, so the negation of
`[](WF_x(A) /\ WF_x(B))` is `<>(<>[]~a \/ <>[]~b)`. `LNEven.simplify` merges
only a directly nested `<><>`, and `toDNF`, which `LNEven` and `LNAll` inherit
from `LiveExprNode`, returns the node unchanged. The disjunction therefore
stays under `<>`, and `classifyExpr` sees `<>(...)` with actions inside and
fails. For `[]WF_x(A) /\ []WF_x(B)`, the negation is a top-level disjunction,
`toDNF` splits it, and each disjunct `<>[]~a` simplifies to an accepted
`<>[]A`. For `[](F /\ G) => FALSE`, the negated property is `[](F /\ G)`
itself, and `classifyExpr` sees `[](... /\ ...)`, which is not split either.

Rewriting `<>(P \/ Q)` to `<>P \/ <>Q` and `[](P /\ Q)` to `[]P /\ []Q` during
normalization would make the two forms equivalent for TLC as they are in TLA.

## Corpus evidence

The `module` corpus84 run has one TLC crash with this cause, `5875e141`. It was
triaged as `NEW`:

```tla
Prop == [](\A q47 \in VariantGetUnsafe("Tag25", ...): WF_FALSE(Head(...)))
```

The domain evaluates to `{"value1_OF_MODEL", "value2_OF_MODEL"}`, so the
`\A` is a conjunction of two `WF_FALSE(...)` formulas under `[]`. TLC prints the
`must be of forms` message and exits 255. Apalache fails, since it does not
support fairness.

Earlier runs may hold more such crashes under the `WF` rows of
[tlc-temporal-formula-limits](../../conformance/tlc-temporal-formula-limits.md),
which were classified by the outermost shape of `Prop`. corpus84 is the first
run where this shape was separated from them. `SF_v(A)` under `[]` is rejected
on its own, so a conjunction of `SF` formulas under `[]` does not show this
defect.

## Expected behavior

TLC checks `[](F /\ G)` as it checks `[]F /\ []G`, and `<>(F \/ G)` as it
checks `<>F \/ <>G`.

## Impact

TLC rejects a well-formed property that it can check in an equivalent form.
A property that quantifies a fairness condition over a constant set inside
`[]`, a natural way to state per-process fairness, is rejected unless the user
moves `[]` inside the quantifier.
