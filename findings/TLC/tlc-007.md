# An invariant evaluation error is reported with the call stack and exit status of a different error

## Summary

When evaluating an invariant on a successor state raises an error, TLC prints
that error's message and trace. It then replays the predecessor under
`CallStackTool` to recover the nested expression positions. The replay does
not reach the same error. Instead, it reports the call stack of whatever the
replay hits next, and when that is an `EvalException` it adopts that
exception's error code as the result. The final report joins two unrelated
errors: the invariant's message, location, and trace, with another action's
nested positions and exit status.

The replay misses the invariant because it re-runs `doNext` on the
predecessor with the same fingerprint set. Line numbers are from
`tlaplus/master` at `1239539` (tag `v1.8.0`, 2026-09-03); the bundled snapshot
is `867aefb`, which behaves as described:

- `ModelChecker.java:523`: `doNextCheckInvariants` catches the evaluation
  error and calls `doNextEvalFailed`, which records the error state with
  `keepCallStack = true` (`:609`), prints the message and trace, and rethrows.
- `ModelChecker.java:291`: after `runTLC` returns, the replay calls
  `doNext(cTool, this.predErrState, ...)`.
- `ModelChecker.java:432` and `:472`: the failing successor's fingerprint is
  already in `theFPSet`, so `isSeenState` reports it as seen, and `:437` skips
  the invariant check for it.
- The replay goes on to later actions of the predecessor, which the original
  run never evaluated because the invariant error stopped it. If one of them
  raises an `EvalException`, `:299-300` prints its call stack as
  `TLC_NESTED_EXPRESSION` and sets `result = e.getErrorCode()`.

The skip applies only to a successor that satisfies the state constraint:
`isSeenState` is called only for such states, so a successor outside the
constraint is never added to the fingerprint set. For that successor the replay
re-checks the invariant, reaches the original error, and prints its call stack.
For a successor inside the constraint there are two cases. If no later action
fails, the replay returns normally, prints no nested positions, and the exit
status stays 76 (`TLC_INVARIANT_EVALUATION_FAILED`). The report is incomplete
but consistent. If a later action does fail, the report is inconsistent. When that action's error is raised by a
standard-module operator, its constant is also one of the unmapped constants
in [`tlc-002`](tlc-002.md), so the invariant failure exits with the generic
status 255 and a consumer records a crash.

The `corpus18` run contains one TLC crash with this cause. TLC printed
`Evaluating invariant Inv failed.` with a no-witness `CHOOSE` message located in
`Inv`, followed by nested positions leading through an action operator to
`Head` of an empty sequence in another disjunct of `Next`, and exited under
2184 `TLC_MODULE_APPLY_EMPTY_SEQ`. See the
[`fabd5358...` input](../../corpus18/02tlc-crash/fabd535842e79ccc1f3366c1c8bff903f2afcbb952afa651d40e5bd1d1b0b431.cbor)
and its [stacktrace](../../corpus18/02tlc-crash/fabd535842e79ccc1f3366c1c8bff903f2afcbb952afa651d40e5bd1d1b0b431.stacktrace).

Observed with the TLC snapshot bundled in FuzzTLA on 2026-09-14
(`tla2tools` 1.8.0-SNAPSHOT, 2026-09-12).

## Reproduction

```tla
---- MODULE Repro ----
EXTENDS Integers, Sequences

VARIABLES x, step

Init == x = TRUE /\ step = 0
Next ==
  \/ x' = FALSE /\ step' = step + 1
  \/ x' \in {Head(<<>>)} /\ step' = step + 1
Inv == IF x THEN TRUE ELSE CHOOSE b \in {} : TRUE
Bound == step <= 4
====
```

with `Repro.cfg`:

```text
INIT Init
NEXT Next
INVARIANT Inv
CONSTRAINT Bound
```

Run:

```sh
java -Xmx512m -cp tla2tools.jar tlc2.TLC -workers 1 -deadlock -noGenerateSpecTE -nowarning Repro
```

TLC exits with status 255:

```text
Error: Evaluating invariant Inv failed.
Attempted to compute the value of an expression of form
CHOOSE x \in S: P, but no element of S satisfied P.
line 10, col 28 to line 10, col 49 of module Repro
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ step = 0
/\ x = TRUE

State 2: <Next line 8, col 6 to line 8, col 35 of module Repro>
/\ step = 1
/\ x = FALSE

Error: The error occurred when TLC was evaluating the nested
expressions at the following positions:
0. Line 9, column 6 to line 9, column 44 in Repro
1. Line 9, column 6 to line 9, column 24 in Repro
2. Line 9, column 13 to line 9, column 24 in Repro
3. Line 9, column 14 to line 9, column 23 in Repro
```

The message and location refer to line 10, the invariant. The nested
positions refer to line 9, the `Head(<<>>)` disjunct, which the checked
behavior never takes. The exit status comes from that disjunct's constant
2184, not from `TLC_INVARIANT_EVALUATION_FAILED`.

Each error alone is reported consistently:

| Change to `Repro` | Report | Exit status |
| --- | --- | ---: |
| none | invariant message, `Head` call stack | 255 (2184) |
| `{Head(<<>>)}` replaced by `{TRUE}` | invariant message, no nested positions | 76 (2111) |
| `Inv == TRUE` | `Head` message and call stack | 255 (2184) |
| the two disjuncts of `Next` swapped | `Head` message and call stack | 255 (2184) |
| `Bound == step <= 0` | invariant message and call stack | 75 (2103) |

The last two rows are the ordering and fingerprint conditions. If the failing
disjunct comes first, the original run and the replay hit the same error. If
the violating successor is outside the state constraint, the replay does not
treat it as seen and re-evaluates the invariant.

## Expected behavior

The call stack and exit status should belong to the error whose message TLC
prints. The replay should re-check invariants on the recorded error state,
or reproduce the failure without consulting the fingerprint set. If replay
cannot reach the original error, TLC should report the error without nested
positions rather than substitute another one.

## Impact

A user debugging the invariant is sent to an expression in an action the
counterexample never takes. A consumer that classifies runs by exit status
sees a different error class than the printed one: here a generic crash
instead of an invariant evaluation failure. A consumer that parses the nested
positions attributes the failure to the wrong operator.
