# Set capability diagnostics can escape as TLC error 1000

## Summary

TLC can diagnose an unsupported operation on an infinite or non-enumerable set
inside a generic `RuntimeException`, report general error 1000, and exit with
status 255. The `corpus3` run contains ten instances across set comparison,
cardinality, difference, intersection, unary union, and set filtering.

The diagnostic itself is TLC's ordinary capability error. It escapes as error
1000 through the root cause of [`tlc-001`](tlc-001.md#root-cause): the error
is raised while TLC fingerprints the initial state, and raised again when the
error handler prints that state, so the handler never classifies it.

The corpus was accumulated with TLC snapshots from 2026.09.04. In the current
bundled snapshot, 2026.09.05.084423, nine representative operations return
specific errors 2103 or 2147 and status 75. Unary union still reproduces the
generic result. `corpus58` adds binary union inside a set of sets; see
[Binary union inside a set of sets](#binary-union-inside-a-set-of-sets). See the [`62082278...` input](../../corpus3/02tlc-crash/62082278f31d9729f4a55d96abdf954a7230769996692006576133eb25d4731c.cbor)
and its [stacktrace](../../corpus3/02tlc-crash/62082278f31d9729f4a55d96abdf954a7230769996692006576133eb25d4731c.stacktrace).

## Reproduction

```tla
---- MODULE UnionString ----

VARIABLE value

Init == value = UNION {STRING}
Next == UNCHANGED value
Inv == TRUE

====
```

Run TLC with `INIT Init`, `NEXT Next`, and `INVARIANT Inv`. The current bundled
snapshot reports:

```text
TLC error code 1000 mapped to exit status 255
Error: TLC threw an unexpected exception.
The exception was a java.lang.RuntimeException
: Attempted to enumerate UNION(s), but some element of s is nonenumerable.
```

`STRING` is not enumerable, so the operation cannot be evaluated by TLC. The
same capability boundary in a set difference, intersection, filter, or finite
set comparison now returns a structured evaluation error and status 75.

## Binary union inside a set of sets

The `corpus58` run adds binary union. Its entry `c27fda4c` assigns an initial
state variable a set of sets whose first element is `(IF TRUE THEN Int ELSE
{...}) \union Int`. It reduces to

```tla
---- MODULE Repro ----
EXTENDS Integers
VARIABLE x
Init == x = {Int \cup Int, {1, 2, 3}}
Next == UNCHANGED x
====
```

Run with `INIT Init` and `NEXT Next`, TLC exits 255:

```text
Error: TLC threw an unexpected exception.
This was probably caused by an error in the spec or model.
See the User Output or TLC Console for clues to what happened.
The exception was a java.lang.RuntimeException
: Attempted to enumerate S \cup T when S:
Int
and T:
Int
are not both enumerable
```

The second element matters. `Init == x = {Int \cup Int}` reports the same
message as an ordinary fingerprinting error, with error call stack and exit
75. A second element makes TLC sort the set when it normalizes it, as in
[`tlc-006`](tlc-006.md#reached-through-set-comparison). A JDWP breakpoint on
`Assert.fail` shows the union raised twice: under `SetEnumValue.fingerPrint`
while `DoInitFunctor.addElement` fingerprints the state, and under
`SetEnumValue.toString` when `ModelChecker.java:193` prints the error state.
The second raise escapes the handler, as described in
[`tlc-001`](tlc-001.md#root-cause). `UNION {STRING}` takes the same path
through `UnionValue.fingerPrint` and `UnionValue.toString`. With one element,
the error is reported through the call-stack replay instead; that path was not
traced.

Reproduced again with FuzzTLA commit `be3d86f` and TLC commit `94d0c50`
(tla2tools `1.8.0-20261006.015956-102`).

Reproduced with FuzzTLA commit `0dcbb309056087d3fc8903ddc4e7aae3c594d130` and
TLC commit `0dab95e` (tla2tools `1.8.0-20261001.024819-90`), bundled in
FuzzTLA, with OpenJDK 25.0.4.1 on Linux aarch64. Apalache was not rerun; it
does not take part in this crash classification.

## Expected behavior

Unary union over a non-enumerable member, and binary union compared while a
set is normalized, should return TLC's ordinary specification-evaluation
failure, as the other set operations now do. A known
finite-value capability boundary must not use the generic system-error status.
Fixing the error handler as proposed in [`tlc-001`](tlc-001.md#expected-behavior)
should restore the specific report for both reproductions; this is untested.

## Impact

The status-255 result causes automated consumers to retain an unsupported input
as a TLC crash. The generic wrapper also obscures which failures are expected
model limitations and which are implementation exceptions.
