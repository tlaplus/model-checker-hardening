# A state variable under `*` in an operator argument of a `RECURSIVE` operator is evaluated as a constant in a liveness property

## Summary

TLC rejects a liveness property that applies a `RECURSIVE` operator to an
operator argument whose body multiplies a state variable. For

```tla
RECURSIVE Rec(_, _)
Rec(Op(_), n) == IF n = 0 THEN Op(n) ELSE Rec(Op, n - 1)
L(k) == k * x = 0
Prop == <>Rec(L, 1)
```

TLC reports `In evaluation, the identifier x is either undefined or not an
operator.` (error 2280) and stops without checking the property. The same
property with `+` in place of `*`, with a non-recursive `Apply(Op(_), n) ==
Op(n)` in place of `Rec`, or with `1 * x = 0` written directly under `<>`, is
checked. `ApaFoldSet` and `ApaFoldSeqLeft`, which `Apalache.tla` defines
recursively, are affected in the same way.

The liveness translation classifies the application as constant-level and
evaluates it once with an empty state. SANY computes the level of
`L(k) == k * x = 0` from the stub definition `a*b == TRUE` in `Naturals.tla`,
which ignores its arguments, so SANY classifies `L` and `Rec(L, 1)` as
constant-level. `Liveness.astToLive` guards against this for operators with
Java overrides by recomputing the level with `getLevelBound`, but that function
returns 0 for an operator argument, so the state variable inside `L` is never
seen.

Observed with tla2tools 1.8.0-SNAPSHOT (Maven snapshot
`1.8.0-20260917.033119-76`), tlaplus/tlaplus commit `142d0ba`; FuzzTLA `56933a3`;
Apalache 0.62.2 (build `f0dec98`), which checks the corpus entry and is not
involved in the rejection.

## Reproduction

`FuzzInput.tla`:

```tla
---- MODULE FuzzInput ----
EXTENDS Integers
VARIABLE x
Init == x = 0
Next == UNCHANGED x
Spec == Init /\ [][Next]_x
RECURSIVE Rec(_, _)
Rec(Op(_), n) == IF n = 0 THEN Op(n) ELSE Rec(Op, n - 1)
L(k) == k * x = 0
Prop == <>Rec(L, 1)
====
```

`FuzzInput.cfg`:

```text
SPECIFICATION Spec
PROPERTY Prop
```

TLC was run through `tlc2.TLC#handleParameters` and `process`, as the FuzzTLA
worker runs it, with `-workers 1 -deadlock -noGenerateSpecTE -config FuzzInput
FuzzInput`:

```text
Error: In evaluation, the identifier x is either undefined or not an operator.
line 9, col 13 to line 9, col 13 of module FuzzInput
```

`process` returns error 2280, which `EC.ExitStatus` maps to exit status 151.
`Rec(L, 1)` equals `L(0)`, which is `TRUE` in the only state, so the expected
result is that the property holds.

Variations, with the module above extended by `Apalache` and
`Apply(Op(_), n) == Op(n)`:

| `Prop` | Operator argument | TLC |
| --- | --- | --- |
| `<>Rec(L, 1)` | `L(k) == k * x = 0` | error 2280 |
| `<>Rec(L, 1)` | `L(k) == x * k = 1` | error 2280 |
| `<>Rec(LAMBDA k: k * x = 0, 1)` | lambda | error 2280 |
| `Rec(L, 1) ~> FALSE` | `L(k) == k * x = 0` | error 2280 |
| `[]Rec(L, 1) \/ <>FALSE` | `L(k) == k * x = 0` | error 2280 |
| `<>ApaFoldSet(L, FALSE, {1, 2})` | `L(a, b) == b * x = 0` | error 2280 |
| `<>ApaFoldSeqLeft(L, FALSE, <<1, 2>>)` | `L(a, b) == b * x = 0` | error 2280 |
| `<>Rec(L, 1)` | `L(k) == k + x = 0` | checked, exit 0 |
| `<>Apply(L, 1)` | `L(k) == k * x = 0` | checked, exit 0 |
| `<>(1 * x = 0)` | none | checked, exit 0 |
| `[]Rec(L, 1)` | `L(k) == k * x = 0` | checked, exit 0 |

`[]Rec(L, 1)` alone is checked because TLC evaluates it as an invariant in each
state rather than through the liveness tableau. In the TLC runs of the
fuzzing corpus, `b * x < 1`, `x * 2 < 1` and `x * x < 1` in a fold combinator
failed in the same way, while `b - x < 1`, `b \div (x + 1) < 1`, `b < x`,
`b = x` and `x > 1` were checked.

## Cause

Line numbers are from `tlaplus/tlaplus` at `142d0ba`, read from the source; the
path was not traced in a debugger.

- `tlc2/tool/liveness/Liveness.java:244-248`: `astToLiveAppl` expands the body
  of a `RECURSIVE` operator only if `getLevelBound` of the application exceeds
  action level. A non-recursive operator is always expanded, which binds `L`
  and reaches `k * x` with its arguments. This is why `Apply(L, 1)` is checked.
- Without the expansion, the application takes the level-based path. SANY's
  level of `Rec(L, 1)` is constant, because the `Naturals.tla` stub
  `a*b == TRUE` makes `k * x` constant-level. `Liveness.java:114-115`
  recomputes it with `getLevelBound`, and `:118-119` then evaluates the
  application with `TLCState.Empty`.
- `tlc2/tool/impl/SymbolNodeValueLookupProvider.java:253` adds the level bound
  of every argument, but `getLevelBound` handles only `OpApplKind`,
  `LetInKind`, `SubstInKind`, `APSubstInKind` and `LabelKind` and returns 0 for
  every other kind (`:209-210`), including the `OpArgNode` that passes `L`. The
  operator's own body, `IF n = 0 THEN Op(n) ELSE Rec(Op, n - 1)`, is scanned
  without the formal `Op` bound to `L`, so it adds nothing either.

The comment at `Liveness.java:50-113` (MAK, 2021-04-16) describes the same
failure for operators whose Java override is paired with a TLA<sup>+</sup> stub
that ignores its arguments, and `getLevelBound` is its fix. `*` has such a stub, and an operator
argument is a path the fix does not follow. `+`, `-`, `\div` and the
comparisons have stubs that mention both arguments, so SANY's level is already
correct for them.

## Corpus evidence

The `module` corpus40 run has one aggregator deviation with this cause,
triaged as NEW: `db6bd5b4`, whose property is

```tla
Prop ==
  (LET Lambda11(parameter9, parameter10) == (parameter10 * step) < 1
   IN ApaFoldSet(Lambda11, FALSE, {1, 2, 3})) ~> FALSE
```

TLC failed with the message above for `step`; Apalache reported the
counterexample, which is correct, since the fold is `TRUE` in the initial state
where `step = 0`. corpus30's `abb1ffd8`, recorded in the
[conformance README](../../conformance/README.md#corpus30-residuals) as not
reduced, has the same diagnostic and a `P ~> FALSE` property whose `P` reads a
variable inside an `ApaFoldSeqLeft` lambda. It could not be re-rendered with
the current FuzzTLA, so its combinator was not inspected.

### How the input was generated

`db6bd5b4` is a mutant two edits away from a PBT input, and the last edit
changed one byte:

| Entry | Generation | Origin | Verdicts |
| --- | ---: | --- | --- |
| `7bd77a46` | 1 | PBT | agree; kept in `04quality-pass` |
| `e3bcb018` | 2 | `random_byte`, `random_byte`, `bitflip` of `7bd77a46` | both pass; kept in `04quality-pass` |
| `db6bd5b4` | 12 | `random_byte` of `e3bcb018` | TLC fail, Apalache counterexample |

The parent already had the whole structure of the property: a fold under
`~> FALSE`, with a `LET`-defined combinator. Its fold was harmless. The
combinator returned its accumulator, and the elements were functions of type
`Str -> Set(Str -> Str)`:

```tla
Prop ==
  (LET Lambda11(parameter9, parameter10) == parameter9
   IN ApaFoldSet(Lambda11, FALSE, { [i \in {"1"} |-> {[j \in {"1"} |-> "1"]}], ... }))
    ~> FALSE
```

The mutated byte changed the decoder's choice of the element type from that
function type to `Int`. The generator then derived the combinator and the set
again from the following bytes, which gave the multiplication by `step` over
`{1, 2, 3}`. So one point edit on an agreeing parent supplied the only
ingredient the parent lacked. It did not add the structure.

`e3bcb018` stayed in `04quality-pass` from generation 2 to at least generation 35
and had 30 mutants: 9 disagreements (this one included), 19 rejected by
the quality gate, 1 quarantined as a known defect and 1 kept. `7bd77a46` had 34
direct mutants over generations 2–39. In corpus40 a mutant's lineage reaches
depth 13, and 12,844 of the 103,364 entries sit at depth 2, as this one does.

## Expected behavior

TLC computes the level of an application with operator arguments from the
levels of those arguments, and checks `<>Rec(L, 1)` as it checks
`<>Apply(L, 1)`.

## Impact

Any liveness property that folds with a combinator that multiplies a state
variable, whether through `ApaFoldSet`, `ApaFoldSeqLeft` or any other
recursively defined operator, is rejected. The failure is a
diagnostic that points at a declared variable, which suggests a scoping error
in the user's specification rather than a TLC defect. In the fuzzing workflow
the entry is recorded as a TLC evaluation failure and an aggregator deviation.
