# Action decomposition materializes a quantifier bound, ignoring the enumeration limit

## Summary

Before model checking starts, `Tool.getActions` decomposes the next-state
relation into actions. For a top-level `\E x \in S` it enumerates `S` through
`EnumerableValue.elements(Ordering)`, and for an `IntervalValue` that call is
`toSetEnum()`, which allocates one `Value[]` slot per element. The allocation
honors no bound: TLC's 1,000,000-element enumeration limit, which rejects the
identical interval everywhere else with `Attempted to construct a set with too
many elements (>1000000)`, is not consulted on this path.

A single `\E i \in 1 .. 411248002` therefore requests a 411-million-element
array during `Tool` construction. The JVM raises `OutOfMemoryError` on that one
request, at roughly 140 MB of a 512 MB heap -- the heap is not exhausted, the
request is simply larger than it. TLC catches the error, abandons the
decomposition, and continues; the run then reports whatever the specification
actually does, with no mention of the failed allocation.

The suppression is what makes this reachable. A JVM started with
`-XX:+ExitOnOutOfMemoryError`, which is how an automated consumer bounds a
worker process, exits on the throw. The same input on a JVM without the flag
completes with an ordinary evaluation error, so the two configurations disagree
on whether the input is a crash.

The `corpus12` run contains one instance. Its next-state relation has a
disjunct `\E actionParam457 \in Cardinality({"model458_OF_MODEL"}) + 0 ..
411248002`, and the run TLC actually performs never enumerates it: the first
disjunct raises `Attempted to apply Head to the empty sequence.` See the
[`1c0ecbd3...` input](../../corpus12/02tlc-crash/1c0ecbd3a9451d84cd266e2023e6beb64ae192ec1d038a7465e6008986120a81.cbor)
and its [stacktrace](../../corpus12/02tlc-crash/1c0ecbd3a9451d84cd266e2023e6beb64ae192ec1d038a7465e6008986120a81.stacktrace),
which records only

```text
TLC worker exited while processing the input
TLC worker stdout:
Terminating due to java.lang.OutOfMemoryError: Java heap space
```

The stored evidence is therefore indistinguishable from [`tlc-004.md`](tlc-004.md),
which exhausts the heap for an unrelated reason. Neither has a triage signature,
and this one must not be given one until the two can be told apart from the
stored text alone.

Observed with TLC snapshot 2026.09.11.074232; the corpus instance was produced
with a 2026.09.10 snapshot.

## Reproduction

```tla
---- MODULE Repro ----
EXTENDS Integers, Sequences

VARIABLE step

Init == step = 0
Next ==
  \/ (Head(<<>>) = 0 /\ step' = step + 1)
  \/ \E i \in 1 .. 411248002 : step' = step
Inv == TRUE
Bound == step <= 5
====
```

with `Repro.cfg`:

```text
INIT Init
NEXT Next
INVARIANT Inv
CONSTRAINT Bound
```

The second disjunct is never evaluated: the first raises before it is reached.
Run:

```sh
java -Xmx512m -cp tla2tools.jar tlc2.TLC \
  -workers 1 -deadlock -noGenerateSpecTE -nowarning -config Repro.cfg Repro
```

```text
Computing initial states...
Finished computing initial states: 1 distinct state generated.
Error: Attempted to apply Head to the empty sequence.
```

Adding `-XX:+ExitOnOutOfMemoryError`, as an automated consumer does to bound a
worker, kills the JVM before initial states are computed:

```text
Starting... (2026-09-11 09:47:56)
Terminating due to java.lang.OutOfMemoryError: Java heap space
```

The failure is a function of the interval size alone. With a 512 MB heap and the
module above, `1 .. 3000000` completes and `1 .. 5000000` terminates the JVM.

The enumeration limit is enforced on every other path. Replacing the module with

```tla
Init == step \in {x \in 1 .. 411248002 : TRUE}
```

reports the bound instead of allocating:

```text
Error: Attempted to construct a set with too many elements (>1000000).
```

Note that `1 .. 1000001` in the `\E` position reports nothing at all, so the
limit is bypassed rather than raised on this path.

## Expected behavior

Action decomposition is an optimization performed before checking. It must not
allocate memory proportional to a quantifier bound, and it must respect the same
enumeration limit as every other enumeration of the same value: an interval
above the limit should leave the action undecomposed, or report
`Attempted to construct a set with too many elements`, not allocate and then
discard a multi-gigabyte array.

Independently, catching `OutOfMemoryError` and continuing silently is not safe.
Whatever the decomposition does on failure, it should report that it gave up
rather than leave the run indistinguishable from one where the allocation never
happened.

## Impact

A specification TLC can check reliably kills a worker JVM that uses
`-XX:+ExitOnOutOfMemoryError` to bound its memory, before checking starts and
regardless of whether the offending action is ever taken. Raising the heap only
moves the threshold, because the allocation is proportional to a constant in the
specification and not to the reachable state space. The consumer records the run
as a checker crash, and the stored evidence -- one `OutOfMemoryError` line -- is
too thin to separate it from an unrelated heap exhaustion.
