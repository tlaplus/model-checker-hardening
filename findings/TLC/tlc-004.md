# A function application makes a bounded CHOOSE keep its set elements lazy and exhaust the heap

## Summary

Applying a function to the result of a bounded `CHOOSE` makes TLC evaluate the
`CHOOSE` and its bound set under `EvalControl.setKeepLazy`. Under that flag TLC
skips the eager conversion of function literals to `FcnRcdValue`, so every
element of the bound set stays a `FcnLambdaValue` that retains a `Context`, the
body node, the tool and a state snapshot. The bounded `CHOOSE` then normalizes
the bound set unconditionally, and the resulting sort calls
`FcnLambdaValue.compareTo`, which re-evaluates the function body through
`toFcnRcd()` once per comparison. Evaluating `(CHOOSE x \in S : TRUE)[a]`
therefore costs several times the memory of evaluating `CHOOSE x \in S : TRUE`
over the same set, for a set well inside TLC's own element bound. TLC reports
error 1001, and a JVM run with `-XX:+ExitOnOutOfMemoryError` terminates.

The code path is in `tlc2.tool.impl.Tool`. Line numbers are from
`tlaplus/master`, which matches the bundled snapshot:

- `Tool.java:2331`, `OPCODE_fa`, evaluates the function subexpression with
  `EvalControl.setKeepLazy(control)`.
- `Tool.java:2377-2378`, `OPCODE_nrfs`, converts a function literal to a
  `FcnRcdValue` only when `!EvalControl.isKeepLazy(control)`.
- `Tool.java:2154`, bounded `CHOOSE`, calls `inVal.normalize()` on the bound
  set before enumerating it.

TLC's set-size guard does not help: the blow-up is element weight and repeated
evaluation, not element count, and the reproduction stays under the
1000000-element bound.

Observed with the bundled TLC snapshot, version 2026.09.05.

## Reproduction

```tla
---- MODULE Repro ----
EXTENDS Integers

ASSUME (CHOOSE x \in {[t \in {"Tag"} |-> [y \in {} |-> 0]] : i \in -900000 .. 0} : TRUE)["Tag"]

====
```

with an empty `Repro.cfg`. Run:

```sh
java -Xmx512m -cp tla2tools.jar tlc2.TLC -workers 1 Repro
```

```text
Starting... (2026-09-05 15:37:10)
Error: Java ran out of memory.  Running Java with a larger memory allocation
pool (heap) may fix this.  But it won't help if some state has an enormous
number of successor states, or if TLC must compute the value of a huge set.
Finished in 01s at (2026-09-05 15:37:12)
TLC error code 1001
```

Adding `-XX:+ExitOnOutOfMemoryError`, as an automated consumer does to bound a
worker, terminates the JVM instead:

```text
Terminating due to java.lang.OutOfMemoryError: Java heap space
```

Removing only the function application, so that the assumption reads

```tla
ASSUME (CHOOSE x \in {[t \in {"Tag"} |-> [y \in {} |-> 0]] : i \in -900000 .. 0} : TRUE) = 0
```

builds and normalizes the same 900001-element set and reports an ordinary
evaluation error in half the heap, `-Xmx256m`:

```text
Error: Evaluating assumption line 4, col 8 to line 4, col 92 of module Repro failed.
Attempted to check equality of the function [Tag |-> <<>>] with the value:
0
TLC error code 2105
```

Measured smallest heap that completes, for the same 900001-element set:

| assumption                                | smallest heap |
| ----------------------------------------- | ------------- |
| `(CHOOSE x \in S : TRUE) = 0`             | 256 MB        |
| `(CHOOSE x \in S : TRUE)["Tag"]`          | 1 GB          |

A JFR allocation profile of the failing run is dominated by
`SetEnumValue.normalize() -> ValueVec.sort() -> FcnLambdaValue.compareTo() ->
FcnLambdaValue.toFcnRcd() -> FcnLambdaValue.evalBody()`, reached through
`Tool.evalApplImpl:2154` under `Tool.evalApplImpl:2331`. The profile of the same
module without the application instead shows `Tool.evalApplImpl:2378`, the eager
`toFcnRcd()` conversion, and no sort at all.

The failure needs a set of *function* literals. Records are unaffected, because
`RecordValue` has no lazy counterpart that `keepLazy` can retain; the record
analogue completes in 256 MB:

```tla
ASSUME (CHOOSE x \in {[t |-> [y \in {} |-> 0]] : i \in -900000 .. 0} : TRUE).t = 0
```

`Variants.tla` defines `Variant(__tagName, __value) == [t \in {__tagName} |-> __value]`,
so a set of variants is a set of function literals and reaches the same path.
This module fails identically, and does so with a scalar payload as well, since
the operator call adds a retained `Context` per element:

```tla
---- MODULE ReproVariant ----
EXTENDS Integers, Variants

ASSUME (CHOOSE x \in {Variant("Tag", [y \in {} |-> 0]) : i \in -900000 .. 0} : TRUE)["Tag"]

====
```

## Expected behavior

Evaluating `(CHOOSE x \in S : TRUE)[a]` should not cost asymptotically more than
evaluating `CHOOSE x \in S : TRUE`. `keepLazy` exists to avoid materializing the
function that is about to be applied; it should not propagate into unrelated
nested subexpressions, and normalizing the bound set of a `CHOOSE` should not
re-evaluate a function body once per comparison.

## Impact

A small, ordinary specification exhausts a 512 MB heap. A consumer that bounds
its checker with `-XX:+ExitOnOutOfMemoryError` loses the worker process and
records the run as a crash rather than as a resource limit, and the trigger, a
`CHOOSE` immediately followed by an application, is a shape a generator produces
routinely. Raising the heap only moves the boundary, since the cost is
`n log n` function materializations in the size of the bound set.
